# GPU coherency: video memory is the truth

GPU results reach video memory only when something reads them, and the display on the host GPU takes them straight from the host's images. There is one host image per texture, with render targets as views of it; UPLOAD; and buffers in main memory the GPU only reads. Command set 2.1 adds volume textures, and 86Box keeps resident buffers. Command set 2.3 adds DOWNLOAD, the GPU's one write to main memory.

The guest sees one video memory. In 86Box the GPU draws on the host GPU, into copies of surfaces held there. This page fixes when those copies and video memory agree, so that everything the guest can observe (a locked surface, the screen, a DOS session's use of video memory) holds the pixels a real card would show.

## The rule

**Video memory is the truth at every point the guest can observe**, except the bytes a host image holds newer pixels for; whatever observes those gets them first. The host's copies are a cache. The guest observes video memory:

1. through the CPU: a DirectDraw Lock, or any other read or write through the framebuffer aperture or the A0000h window (GDI's drawing on the desktop, the mini-VDD, the BIOS);
2. through the display engine, which scans out video memory.

## What the device tracks

- **CPU writes.** Every guest write to video memory through the framebuffer aperture (BAR1) or the extended-mode A0000h window advances a write counter for its 4 KB page; in 86Box these writes pass through the device. The GPU's own writes to video memory (2D, copies back) advance a second counter per page, so each counter has one writer; a page's version is their sum. Writes made in VGA modes go through 86Box's VGA core instead and are not counted: the drivers reset (and hold) the GPU before a VGA mode takes the screen and before every mode change, and a reset drops every host copy, so nothing stale survives ([gpu-registers.md](gpu-registers.md)).
- **Host copies.** For each surface the GPU has used, the device keeps a host image, keyed by the surface's description (offset, width, height, pitch, format; for textures, the offsets and pitches of every mip level of every face). One image holds a whole texture: a render target or depth buffer whose description is exactly one level or face of a texture's image is drawn into that image, as a view of it, not into an image of its own. For each image it records the page counters as of its last upload, and, per level and face, the region the GPU has drawn but not yet copied back (its "GPU-newer" region).
- **Volume textures (command set 2.1).** A volume has a host image of its own (a 3D image), keyed by its description (format, size, depth, and every level's offset, pitch and slice pitch), with the page counters of every page from its first level's first byte to its last level's last. It is never drawn into, so it never holds GPU-newer data, and it takes no part in the rules for images below: before a draw samples it, it is uploaded whole when any of those pages changed; a DISCARD over its bytes drops it; it is evicted like an image, and when the volumes hold 64 or a quarter of the host images' budget. A target drawn over a volume's bytes is an image of its own, and the volume sees what it wrote once those pixels are copied back to video memory.
- **The GPU-newer page map.** For each 4 KB page, how many images hold GPU-newer pixels there (each counts the pages from its region's first row's first pixel to its last row's last). The device checks it on every guest access through the framebuffer aperture and the A0000h window: an access to a page it counts waits while those images copy their GPU-newer pixels back, then goes ahead on current bytes. The guest's CPU therefore never reads or writes a page the GPU holds newer pixels for. (The wait is bounded: a host GPU that does not answer within about two seconds lets the access go ahead without its pixels, and the event is logged; the pixels may then land over what the access wrote.)

## 2D on the host CPU

In 86Box the 2D packets (FILL, BLT, UPLOAD) run on the host's CPU, directly on the bytes of video memory: they are exact for every format (palette indices, depth values, colour keys on raw bits). Before one runs, every host image holding GPU-newer data in its source or destination bytes copies it back (as for SYNC). Its writes then count as writes for every host image of those bytes, exactly as the guest's own CPU writes do: each image sees the new pixels the next time it is used. An UPLOAD also writes the new texels straight into every host image of the surface it fills that was current but for that write, and keeps the image current, so no upload of it follows (a palettized texture, whose conversion needs the palette of its next use, uploads again then): the result is the same.

## Before the GPU uses a surface

Before a packet reads a surface or writes part of one (a BLT source or destination, a FILL or CLEAR target, a texture, the render target and depth buffer), the device uploads every part of the surface whose pages changed since the host image was last brought up to date. A surface the device has never seen is uploaded whole. Only a packet that overwrites the whole surface (a FILL or CLEAR of its full extent) skips the upload.

If another host image covers any of the same bytes and holds GPU-newer data there, that data is copied back to video memory first, then the upload proceeds. Two descriptions of the same bytes (a surface read with a different pitch, a texture whose levels are described differently) therefore always see each other's results. A texture and a render target that is one of its levels or faces are not two descriptions: the target is the texture's image, so rendering into a texture and then sampling it copies nothing.

When the device makes the image of a texture whose level or face already has an image of its own (a render target drawn into before the texture was first used), that image's pixels move into the texture's image on the host GPU and the smaller image is dropped. (Between images of different host formats they go through video memory instead.)

A depth image in a 32-bit float format converts its values on every upload and copy back by what it holds, Z or W ([gpu-formats.md](gpu-formats.md)), W with the W range at that time: the guest's bytes are always the reference's form on its grid, so a Lock, a 2D packet or another image sees the depth buffer as a card of the guest's format would hold it. Because that form holds less than the image (W), such an image keeps a copy of its bytes as of its last upload or copy back: when its pages change, only the pixels on the pages that changed whose bytes differ from that copy go up again, and those a FILL, BLT or UPLOAD wrote whatever their bytes (each row's runs of them, in copies of up to 4,096 rectangles); the rest keep what the image holds (a page it shares with the next surface changes without any of its pixels doing so). A guest CPU write of the very bytes the copy holds goes unseen: the form in video memory can repeat its values (with an infinite range every W reads 0), but a program writes a W-buffer's bytes with its CPU only to set them. Its own GPU-newer pixels go back to video memory first only when a run of changed pixels reaches the rectangle that holds them. A copy back also keeps current other images (eight at most) that share its first or last page but have no byte in the span it writes, its pitch gaps included, so two surfaces side by side do not make each other stale. When a depth image moves to the float format for W-buffering, its GPU-newer pixels go back to video memory first and the float image is uploaded from there, like any image made for bytes that already hold pixels. An image evicted and made again starts from video memory's form.

**Drawing with transformed vertices**, the device does not know on the host CPU where the primitives land: a draw marks the whole scissor rectangle (the viewport within the target) as GPU-newer. A draw from pre-transformed vertices marks the bounds of the positions in its window of vertices (one pixel more on each side, within the scissor), and the origin when it uses a vertex the card has no number for, which reads as 0.

## When GPU results reach video memory

The GPU's results are copied back from a host image to video memory when something reads them, and only then:

| When | What |
|---|---|
| A SYNC packet | The GPU-newer parts of every image overlapping the packet's byte range |
| A DOWNLOAD packet (command set 2.3) | The same for the rectangle's bytes, before they go to main memory |
| The guest's CPU reads or writes a page in the page map | The GPU-newer parts of every image counting that page |
| Another image or a 2D packet needs the same bytes | Before it uses them (above) |
| The device evicts an image | Its GPU-newer parts, first |
| DISCARD | The GPU-newer parts of overlapping images that lie outside the discarded range; what lies inside is dropped |
| RESET | All of them, before the device drops its images: video memory keeps all the GPU drew, as a real card's would |

A FENCE packet completes only after the work of the packets before it. The driver's sequence for letting the CPU see a surface is still SYNC over the surface, FENCE, wait for the fence; a CPU access without it gets the pixels through the page map.

## The screen

The display engine's frame is shown by the device on the host GPU ([gpu-registers.md](gpu-registers.md), the display): from a mirror of video memory, which takes the pages that changed, and from a layer the device copies GPU-newer pixels into, on the host GPU, at their video memory offsets. At a FLIP the new frame's GPU-newer pixels go to the layer before the frame is shown; at the end of each batch, those of the frame on the screen; each time only the images drawn since they last went there. A pixel inside a rectangle in the layer is shown from the layer while its image holds it newer; once the image is copied back, from video memory. Where the host keeps a format differently from the guest (as floats), or while 86Box shows the frame itself (a VGA mode, a host GPU failure), those pixels are copied back instead, as before.

A copy back writes only the GPU-newer region, row by row, so CPU writes elsewhere in the surface survive. It is not a CPU write for the image it came from (that image is up to date), but it is for every other host image of the same bytes: those see the new pixels the next time they are used.

## Memory that changes owner

DirectDraw reuses its heap: the bytes of a destroyed surface soon belong to another. The driver sends **DISCARD** for a surface's bytes when DirectDraw destroys it ([directx-hal.md](directx-hal.md)). The device drops every host image overlapping them; an image that extends beyond the range first copies back its GPU-newer data outside it. A dead surface's pixels can then never land on its successor, and nothing else is lost.

The device may also evict any image at any time, least recently used first, after copying back its GPU-newer parts, to keep its host memory bounded. Eviction is invisible to the guest.

## Main memory the GPU reads (interface 3.0)

Vertex buffers, index buffers and UPLOAD sources at GPU addresses are guest RAM the GPU reads through its page table ([gpu-registers.md](gpu-registers.md)). The GPU never writes them, so they have no GPU-newer state and nothing is ever copied back to them. The one memory the GPU writes there is a DOWNLOAD's destination (command set 2.3: [gpu-commands.md](gpu-commands.md)): the DirectX driver's copies of surfaces it Locks through main memory, in the pool but no buffer's. A DOWNLOAD writes video memory's bytes, its GPU-newer pixels copied back first, when it executes; the driver waits for its fence before the program reads the copy, sends the copy back with UPLOAD at the Unlock, and frees a copy only once the packets that read or write it are done ([directx-hal.md](directx-hal.md)). The guest's CPU writes them at full speed, without the device seeing it, so the rules are the driver's:

- A packet reads the memory when it executes, not when it is queued. The driver lets no one write memory a queued packet still reads: it keeps the fence after the last packet that used each buffer, as it does for surfaces, and a Lock waits for it (or hands back other memory: [directx-hal.md](directx-hal.md)). A Lock no queued packet reads keeps the buffer's memory. Memory a Lock gave up stays the buffer's, as one of its 2 spares (or goes back to the pool), and is handed out again only once the packets that read it are done; new memory never holds another buffer's bytes, as a fresh block gets the buffer's contents copied in. A DirectX 6 or 7 draw that reaches the driver while its vertex buffer is locked for writing was issued before the Lock. Under a NOOVERWRITE Lock, which promises to leave what queued draws read, it reads the buffer in place under a new version; under any other write Lock it must read the contents from before the Lock: the old block when the Lock renamed the buffer, which the driver keeps until the Unlock (or the buffer's end; a rename while that Lock is open keeps the first Lock's block) and frees on the fence of the last packet that read it, read under its old version; else its vertices go through the ring before the program can write. A buffer once drawn so is renamed at its later plain write Locks, busy or not, when a block can be had at once, the contents copied and the old block kept the same way.
- STREAM and INDICES carry a version that changes whenever the buffer's contents may have changed, and is never used twice for the same address (the driver draws versions from one counter for the whole system, so memory freed and given to another buffer never matches an old copy). The device may keep a host copy of a buffer and read guest RAM again only when the address, the size or the version changes; the inline buffer is always read as it is. STREAM's size bounds what a draw may read (a vertex past it reads as 0), not what the device must copy: the DirectX driver names a vertex buffer from the call's first vertex to the buffer's end ([directx-hal.md](directx-hal.md)), so a host copy covers only the windows draws actually read, and a buffer appended to between draws is copied a piece at a time.
- **Resident buffers** (86Box): the device keeps whole copies of buffers at GPU addresses in one host buffer, its arena (64 MB), by where they end (address plus size) and their version, each from the lowest start a draw named (the DLL names a DirectX 7 buffer from the call's vertex offset, a DirectX 8 one from a draw's first vertex: a higher start is read in the same copy, a lower one puts the buffer in again from there). A buffer goes in when a draw of a later host recording than the first draw that read it reads it again (the same end and version), if it is at most 8 MB and the page table maps it all (one read once, or whose version moves at every Lock, as a dynamic buffer's does, is usually drawn within one recording and read per draw as before); older versions of it, and copies of this version from a higher start, go then. Draws then read its vertices, or its indices, there, and copy nothing from guest RAM. A draw of transformed vertices drawn one vertex per invocation (no WRAPn, point fill, wireframe or line band), whose streams and index buffer are all resident and whose indices lie within their buffer (32-bit ones only where the host takes any 32-bit index value), goes straight from the arena: the host reads the indices and adds the draw's base itself, and no index is read on the CPU. None does while a capture's draw census records. For room, the least recently used buffer that no pending host submission reads (each submission judged by its own fence) goes, with the idle ones beside it until the gap holds the new one. A buffer at an address the page table does not map stays out (the draw reads it per draw, and fails as before).
- **The rule's check** (Diagnostics "DirectX 7: vertex audit" and "DirectX 8: stream + texture audit (slow)"): the device compares the window of each resident buffer a draw reads (its vertices, or its indices) with guest RAM, at most once a second a buffer (a NOOVERWRITE Lock's writes elsewhere in the buffer are not in the window); one that changed without a new version (a guest breaking the rule) is named, counted (`summary buffers resident`), and read from guest RAM again from the next draw. No draw goes straight from the arena under these settings: each draw's window is checked. Its counterpart for textures in video memory, the stale-texture check (Diagnostics "DirectX: texture audit" and "DirectX 8: stream + texture audit (slow)": [registers.md](registers.md)), hashes a texture's levels and faces at upload (and at the next check after a copy back, an UPLOAD's rectangle or a packet overwriting the image) and compares them at a draw, at most once an interval a texture (a second, longer while its budget runs out), whatever their pages' recorded versions say: bytes that changed without an upload of them (a write the counters missed, or versions recorded as current without one) are named when two checks running find them, once per upload, and nothing is repaired, so the host draws what it holds until the pages' versions move.
- A RESET drops every host copy of these buffers.

## What the guest must do

These are the rules a real card of the period imposed too, and Direct3D 6.1 and DirectDraw already follow them:

- **Read GPU results only after synchronizing.** DirectDraw's Lock is the way: the driver's Lock callback issues SYNC and FENCE, and waits ([directx-hal.md](directx-hal.md)). A surface read without a Lock may show older pixels.
- **Do not write a surface the GPU may still use.** A packet uploads what it reads when it executes, not when it is queued, so the driver's Lock waits for the fence after the last packet that used the surface in any way: read, written, or due to be shown by a FLIP.
- **GDI on the desktop.** Before the DIB engine draws on the screen, the display driver's access callback waits for the last fence issued so far ([directx-hal.md](directx-hal.md)); GPU-newer pixels on the screen reach video memory through the page map when GDI touches them.

## Order and timing

- The device may do the work of several packets at once and in any order internally; the results in video memory and in FENCE must be as if each packet finished before the next started.
- Copies back and the 2D packets are the only times the device writes video memory. The ring itself is only ever read by the device.
- Uploads and copies back happen on the GPU's own time; the guest sees their cost only when it waits on a fence.

## Cost

The design keeps copies to the points where the guest looks. A game's frames go from the host image to the screen without leaving the host GPU; nothing is copied back unless the guest's CPU, a SYNC or a 2D packet reads those bytes. Textures are uploaded once and again only when the guest writes them. Drawing itself (rasterization, texturing, blending, depth and stencil) is done entirely by the host GPU.
