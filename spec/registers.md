# Registers

The card's registers. The VGA registers themselves (sequencer, CRT controller, graphics and attribute controllers, DAC) are the standard IBM VGA set, implemented by 86Box's VGA core.

## BAR0: register window (64 KB)

All registers are 32 bits, little-endian, and also readable as bytes or words. The window also holds the GPU's registers (interface 3.6): [gpu-registers.md](gpu-registers.md). The first four are unchanged in meaning:

| Offset | Name | Value |
|---|---|---|
| 00h | ID | 38394756h: the bytes `VG98` |
| 04h | Hardware version | 00030006h: interface 3.6 (PROFILE.VSYNC and VSYNC_CONTROL, the V-sync overrides: [gpu-registers.md](gpu-registers.md)); 3.5, PROFILE.GAMMA and the gamma table's registers, read 00030005h; 3.4, PROFILE.CURSOR and the hardware cursor's registers, read 00030004h; 3.3, PROFILE.DOWNLOAD, with command set 2.4 PROFILE.GLIDE and with command set 2.5 PROFILE.OGL, read 00030003h; 3.2, PROFILE.PROGRAMS, read 00030002h; 3.1, PROFILE.FIXED8 and the 64 MB aperture, read 00030001h; 3.0, the vertex pipeline and the GPU's page table, read 00030000h; 2.2, the status block in main memory, read 00020200h; 2.1 00020100h; 2.0 00020000h; 1.0 00010000h) |
| 08h | Profile | What the GPU can do ([gpu-registers.md](gpu-registers.md)); 0 means VGA and display engine only |
| 0Ch | VRAM size | VRAM in bytes (8, 16, 32, 64 or 128 MB, from 86Box's settings) |
| 10h-6Ch | | The GPU's registers ([gpu-registers.md](gpu-registers.md)) |
| 70h-78h | | The hardware cursor's registers (interface 3.4: [gpu-registers.md](gpu-registers.md), The hardware cursor) |
| 7Ch-80h | | The gamma table's registers (interface 3.5: [gpu-registers.md](gpu-registers.md), The gamma table) |
| 84h | | VSYNC_CONTROL, the V-sync overrides (interface 3.6: [gpu-registers.md](gpu-registers.md), The V-sync overrides) |
| 88h-FFFCh | | Reserved, read 0 |

The drivers find BAR0 through the display engine's REGS_BASE register ([display-engine.md](display-engine.md)), as they find BAR1 through LFB_BASE.

## BAR1: framebuffer (128 MB aperture)

A direct window onto VRAM: offset N is VRAM byte N. Offsets beyond the installed VRAM read FFh and ignore writes. It is 128 MB whatever the VRAM size. The display engine's modes and the drivers use it; the VGA modes go through the A0000h window.

## Display engine registers

Sequencer indices 80h-BFh hold the display engine's registers: [display-engine.md](display-engine.md).

## Developer debug registers

| Where | Access |
|---|---|
| Sequencer index E0h (3C4h/3C5h) | Write: one character of debug text. Line feed (0Ah) ends a line, carriage return (0Dh) is ignored, other non-printable characters become `?`. Read: 01h while the log is on, 00h while it is off. |
| BAR0 50h (DEBUG) | A 32-bit write: its low byte is one character, as above, for a line of its own. A write of VGPU98_DEBUG_CAPTURE (5041430Dh) is no character: the DirectX driver asks for a capture after the line naming a fault it caught (with bit 0, below; [directx-hal.md](directx-hal.md), Faults inside the DLL); with captures on, the GPU starts one as for an error it refuses. Its low byte, a carriage return, is what a device without it sees, and ignores. A write of VGPU98_DEBUG_IDLE (4C44490Dh) is none either: with the log on, the DirectX driver's last Direct3D context went, which the watchdog takes as the end of drawing (below). Read: bit 0 (VGPU98_DEBUG_LISTENING) while the log is on at a full level ([Diagnostics](#diagnostics): every one but **Minimal**, **Glide**, **OpenGL** and **Display**, at which SR E0h reads 01h all the same); bit 1 (VGPU98_DEBUG_AUDIT) with the **DirectX 7: vertex audit** and **DirectX 8: stream + texture audit (slow)** settings, which have the DirectX driver audit its calls' vertex ranges; bit 2 (VGPU98_DEBUG_AUDIT8) with **DirectX 8: stream + texture audit (slow)** alone, which adds the audit of DirectX 8's draws; bit 3 (VGPU98_DEBUG_SHADERS) with **DirectX 8 shaders: Capture** while the log listens (bit 0), with which the DirectX driver logs each shader's instructions, and bit 4 (VGPU98_DEBUG_SHADERS14) too with **Capture, with GPU programs**, with which it logs each shader's GPU program as well; bit 5 (VGPU98_DEBUG_EVENTS) at **Minimal**, **Glide**, **OpenGL** and **Display**, with which the DirectX driver counts nothing and writes its event lines alone ([directx-hal.md](directx-hal.md), The DirectX 8 interface, Diagnostics); bit 6 (VGPU98_DEBUG_TEXTURES) with **DirectX: texture audit** and **DirectX 8: stream + texture audit (slow)** while the log listens (bit 0), which the DirectX driver names in a line at its start; bit 7 (VGPU98_DEBUG_GLIDE) at **Glide** alone, with which the Glide DLLs write every line of theirs, not only their event lines ([glide.md](glide.md), The log); bit 8 (VGPU98_DEBUG_OPENGL) at **OpenGL** alone, with which the OpenGL ICD writes every line of its, not only its event lines ([opengl.md](opengl.md), Diagnostics); the other bits 0 (each level's value: below). For 32-bit code (the DirectX driver, the Glide DLLs: [glide.md](glide.md)), which must not touch the sequencer index the 16-bit driver uses |

The registers are live whenever the card's **Diagnostics** setting is not Off. The BIOS, the display driver and the mini-VDD write to SR E0h; the DirectX driver DLL, the Glide DLLs and the OpenGL ICD write to DEBUG, one line at a time under the shared block's line lock ([glide.md](glide.md), The log). Each finished line appears in 86Box's log on the host as `<date> <time> VGPU98 debug: <text>`. Every line of the display driver, the mini-VDD and the DLLs starts with its name and **build stamp**, the commit the drivers were built from (`-dirty` with uncommitted changes, `unknown` outside git): `VGPU98 driver 1a2b3c4: …`, `VGPU98 VxD 1a2b3c4: …`, `VGPU98 DLL 1a2b3c4: …`, and with the program's file name `VGPU98 glide2x 1a2b3c4 GAME.EXE: …` (`glide3x`; the OpenGL ICD's `VGPU98 opengl 1a2b3c4 QUAKE2.EXE: …`), so a log shows which build of each file is installed. When DirectDraw's driver object cannot be created, the display driver says why: `vgpu98dx.dll did not start (missing, damaged or not loaded); DirectDraw and Direct3D unavailable` (SetInfo failed and the DLL never ran DriverInit), `DirectDraw refused the driver description (SetInfo)`, `DirectDraw never registered its callbacks (DDNEWCALLBACKFNS)`, or `DDCREATEDRIVEROBJECT without an output buffer`. The DLL says why it gives less than full acceleration: the shared block is from another build, the GPU's registers are not mapped or speak another interface version, or the GPU has no 3D. The mini-VDD and the DLL name where the command ring is: `ring buffer ready: 2048 KB in main memory` (or `no ring buffer …`), then, at the full levels ([Diagnostics](#diagnostics)), `ring 2048 KB in main memory` or `ring 128 KB in video memory (` the reason `)`. Nothing is written inside the virtual machine. 86Box writes its log to standard output, or to the file given with `86Box.exe --logfile <path>` (`-L`); on Windows, use `--logfile` to see it. With the register not live, writes to index E0h are ignored and reads return 00h, so software can tell whether the log is listening.

A line longer than 159 characters is logged in pieces of 159. A machine reset, or closing 86Box, logs any unfinished line as it stands.

What DEBUG reads at each [Diagnostics](#diagnostics) level:

| Setting | DEBUG reads |
|---|---|
| Off | 0 |
| Minimal | 20h (EVENTS) |
| DirectX, DirectX + capture, Developer: every packet (slow) | 01h (LISTENING) |
| DirectX: texture audit | 41h (LISTENING, TEXTURES) |
| DirectX 7: vertex audit | 03h (LISTENING, AUDIT) |
| DirectX 8: stream + texture audit (slow) | 47h (LISTENING, AUDIT, AUDIT8, TEXTURES) |
| Glide | A0h (EVENTS, GLIDE) |
| OpenGL | 120h (EVENTS, OPENGL) |
| Display | 20h (EVENTS): Display has no bit of its own, as nothing changes inside the VM |

With **DirectX 8 shaders** at **Capture** a level that reads LISTENING adds 08h (SHADERS), at **Capture, with GPU programs** 18h (SHADERS, SHADERS14) ([86Box settings](#86box-settings)).

### Display check

At the texture audit's levels each FLIP ends a frame, and the renderer takes the start the FLIP shows. Each draw counts for its frame, and also counts as on display when its colour target's offset is that start. At the next FLIP the frame is judged: a frame with draws is looked at, and it was drawn on display when more than half its draws were (a cursor or an overlay drawn there is not enough); a frame without draws is passed over. Eight such frames in a row are a finding, once per run of them, as the stale texture is (above): `VGPU98 3D: texture audit: possible drawing into the surface on display:` n `of` n `draws a frame went to the surface the last FLIP showed (`its offset`), 8 frames running`, the counts the eighth frame's. Its capture's packets show the FLIP and TARGET order. A game that never flips is never looked at (a loading screen drawn into the front buffer, a windowed game, GDI), and a reset that starts a new session starts the count again. The summary's findings name it `drawing on display`, and the `texture coordinates` summary line ends with `frames looked at for drawing on display` n`, drawn mostly into the surface on display` n.

### Vertex race detector

At the texture audit's levels the DirectX driver sends a VSUM note before each draw that reads a pool buffer's stream by GPU address, and for a DirectX 8 draw one for its pool index buffer: the window the draw reads, hashed as the driver sent it, the buffer's audit id, and the buffer's Locks since its last note ([gpu-commands.md](gpu-commands.md), NOP; [directx-hal.md](directx-hal.md), Diagnostics). At the note the GPU hashes the same bytes where the draw reads them: the arena's copy when the arena of resident buffers holds the stream (or the index buffer) at that version, else guest RAM through the page table. It hashes guest RAM in either case. These are findings, as the stale texture is (above), each line after `VGPU98 3D: texture audit:`:
- what the draw reads changed: a race, named and captured when it is found: `possible vertex race` n`:` `stream` s or `the index buffer` `changed between the driver's call and the GPU's read in parts` the parts that differ `of 8 (`n `bytes from byte` n`, GPU address` a`, stride` n`, version` v`, buffer` its audit id, with `; until lately, buffer` id`'s memory` when notes named another buffer in the same memory (by its end) within the last 65,536 notes (a pointer kept into memory renamed away, then reused), `; drawn from` `guest RAM`, `the arena's copy` or `the arena's copy, guest RAM too``); Locks before the draw:` its note's Locks`; those after it: a later line`, n being the note's sequence number;
- the arena's copy differs and guest RAM does not: `possible stale arena copy:` `stream` s or `the index buffer` `'s resident copy (GPU address` a`, version` v`) differs from what the DirectX driver drew in parts` the parts `of 8 (`n `bytes from byte` n`), guest RAM does not; draws read the copy`.

A race is then held for the Locks given after its draw, by the buffer's audit id (by the buffer's end for one without an id), 64 at most. The command processor gives each note its place in the ring and how far the driver had written when the packet began. The buffer's later notes, from later draws, add their Locks together, up to and including the first note the driver wrote after the GPU read the race's note: those hold every Lock given between the draw and the read, as no Lock comes inside a DrawPrimitives2 call. A refused note of the buffer (by its id) adds its Locks too. A named race then gets a second line, by the process that drew it: `possible vertex race` n`, the buffer's Locks after the draw, to its first draw past the GPU's read:` the Locks. One still held after 4 frames or 16,384 notes, or the oldest when 64 are held and another is found, is told with what came: `possible vertex race` n`, the buffer's Locks after the draw (its draws past the GPU's read not seen):` the Locks, or `possible vertex race` n`, the buffer's Locks after the draw: no later draw of the buffer seen`. A reset that starts a new session drops those held, counted.

Locks read `none` (with ` (one open at a draw)` for a Lock still open), or their number (` or more` at 255) and `, flags` their DDLOCK flags together, then those that apply of `, NOOVERWRITE given with a draw pending` or `, given unwaited with a draw pending`, `, given with none pending`, `, given after a wait`, `, given new memory` and `, one open at a draw`. A window changed in guest RAM only, while the draw reads the arena's copy made before, is counted, not told. The summary's findings name them `vertex races` and `arena copies`. Every summary adds, while any note was checked or refused or a race dropped: `VGPU98 summary texture races:` n `vertex and index windows checked (`n `MB),` n `changed before the GPU read them (`n `in every part,` n `in memory another buffer held lately); races told by the buffer's Locks between the draw and its next: NOOVERWRITE given while a draw was pending` n`, another given so` n`, one given with none pending` n`, one that waited` n`, new memory only` n`, none but one open` n`, none` n`, no later draw` n `(told early for room` n`, dropped at a reset` n`); changed in guest RAM only (the arena's copy drawn)` n`; arena copies differing` n`; notes refused:` n `naming no stream or not readable,` n `damaged or out of sequence`. A race is counted, when it is told, under the first of those kinds its later Locks hold. A note names no stream when its stream, or for the index buffer the INDICES binding, is not at a GPU address, has another stride (index size) or ends past the buffer; it is not readable when the page table cannot read its window; it is damaged or out of sequence when its check word does not match or its sequence is not above the last.
