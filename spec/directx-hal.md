# DirectX 6.1, 7 and 8 driver interface

**Covers:** the DirectDraw and Direct3D driver interfaces: DirectX 6.1's; execute buffers in the pool, the DirectX 7 interface and system-to-video blits; the DirectX 8 interface ([below](#the-directx-8-interface)).

How Windows 98 SE's DirectDraw and Direct3D (the DirectX 6.1 runtime, and DirectX 7 runtimes installed later) find and drive the card. The interfaces are restated from the Windows 98 SE and DirectX 7 DDKs, their DirectDraw documentation, and the DirectX 6.1 SDK headers, used as references for facts only. The DDK's S3 ViRGE and Permedia 2 samples, the reference rasterizer, and the open-source vmdisp9x/vmhal9x driver were read to confirm how the pieces meet in practice. What the driver tells the runtime it can do is in [d3d-caps.md](d3d-caps.md); what it sends the GPU is in [gpu-commands.md](gpu-commands.md).

## The pieces

| File | Role |
|---|---|
| `vgpu98.drv` (16-bit, [win98-display-driver.md](win98-display-driver.md)) | Answers DirectDraw's escapes, describes video memory and the modes, builds the DirectDraw driver description, sets modes. Maps BAR0 for the DLL. Stops the GPU around mode changes and full-screen DOS sessions |
| `vgpu98dx.dll` (32-bit, new) | Every DirectDraw and Direct3D callback: turns them into GPU packets in the ring |
| `vgpu98.vxd` ([minivdd.md](minivdd.md)) | Lets the GPU finish, resets and holds it before a VGA mode takes the screen (a full-screen DOS session, the blue-screen messages); lets go when the desktop is back |

The DLL and the 16-bit driver share one block of memory in the 16-bit driver's data segment (fixed and locked, so its linear address never changes): the **shared block** (`driver32/shared.h`). It holds:

- the linear addresses of the framebuffer (BAR1) and the registers (BAR0), and the current mode;
- the DirectDraw driver description and its callback tables, with the 32-bit callback addresses the DLL fills in;
- the **ring lock**: a spinlock taken with `lock cmpxchg` from either side, holding its owner's process ID and when it was taken;
- the last fence value issued, and the fence of the last flip;
- the last version given the contents of a buffer in the pool (one counter for every process, as long as Windows runs: [gpu-coherency.md](gpu-coherency.md));
- the last sequence number given the DLL's audit notes (`note_seq`; [gpu-commands.md](gpu-commands.md), NOP), which lasts as long as the display driver, so a DLL loaded again goes on counting where the last left and the GPU, which takes notes in increasing order, keeps taking them;
- the host log's line lock (`log_lock`: 0 free, 1 held), which every line written to BAR0's DEBUG register takes, the DLL's in every process and the Glide DLLs' ([The 32-bit DLL](#the-32-bit-dll), [glide.md](glide.md)). It is the first of what were two reserved dwords after `note_seq` (one stays reserved), so the block's layout, size and version (2) are unchanged.

The Glide DLLs find the block too, through the display driver's VGPU98_ESC_INFO escape ([win98-display-driver.md](win98-display-driver.md), The Glide DLLs' escape), for the registers, video memory's address and size, the current mode (and its `mode_serial`, which a mode change moves) and the mode list, the line lock, and the ring: they are its second kind of client ([The 32-bit DLL](#the-32-bit-dll), [glide.md](glide.md)).

Whether the GPU may be used at all is not in the shared block but in the GPU: its hold bits ([gpu-registers.md](gpu-registers.md)), which the mini-VDD can set too.

The block's first five fields (its magic, version and size, then the framebuffer's and the registers' linear addresses) keep their offsets in every version. A DLL handed a block of another version or size refuses it (DriverInit returns 0; a Glide DLL reports no board), but can still reach the register window to say in the log that the display driver is from another build.

Its exact layout is the project's own.

## The handshake

DirectDraw (DDRAW.DLL with its 16-bit half DDRAW16.DLL) talks to the display driver through GDI's Control escape. In the order DirectDraw uses them:

1. **QUERYESCSUPPORT (8)** for function **DCICOMMAND (3075, 0C03h)**: the driver returns **DD_HAL_VERSION, 00FFh**, saying it has a DirectDraw HAL.
2. **DCICOMMAND** escapes. The input is a DCICMD:

   | Offset | Field | |
   |---|---|---|
   | 0 | dwCommand | the DirectDraw command (below) |
   | 4 | dwParam1 | |
   | 8 | dwParam2 | |
   | 12 | dwVersion | DD_VERSION, 200h. Any other value: the escape is passed to the DIB engine |
   | 16 | dwReserved | |

   The commands come in this order:

   | dwCommand | Name | What the driver does |
   |---|---|---|
   | 12 | DDNEWCALLBACKFNS | dwParam1 is a 16:16 pointer to DDHALDDRAWFNS: `dwSize`, `lpSetInfo`, `lpVidMemAlloc`, `lpVidMemFree`. The driver keeps `lpSetInfo`, a 16-bit far Pascal function `BOOL SetInfo(LPDDHALINFO, BOOL reset)` in DDRAW16. Returns 1 |
   | 13 | DDVERSIONINFO | dwParam1 carries the runtime's version. The driver fills the output DDVERSIONDATA (`dwHALVersion`, two reserved dwords) with 050Ah, the Windows 98 SE DDK's DD_RUNTIME_VERSION (informational; the DirectX 7 DDK's is 700h). Returns 1 |
   | 11 | DDGET32BITDRIVERNAME | Fills the output DD32BITDRIVERDATA: `szName` (260 bytes) "vgpu98dx.dll", `szEntryPoint` (64 bytes) "DriverInit", `dwContext` (offset 324) the shared block's linear address. Returns 1 |
   | 10 | DDCREATEDRIVEROBJECT | Builds the DDHALINFO (below) and calls `SetInfo(&halinfo, FALSE)`. On success writes the driver's instance handle as a DWORD to the output and returns 1; otherwise returns −1 |

3. After DDGET32BITDRIVERNAME, DirectDraw has its helper process DDHELP.EXE load the DLL and call **`DWORD __stdcall DriverInit(DWORD dwContext)`** with the context. DriverInit stores its 32-bit callback addresses and the Direct3D pointers in the shared block, sets its "started" flag (`dll_ready`), and returns nonzero (0 refuses). DirectDraw goes on to DDCREATEDRIVEROBJECT even when the DLL could not be loaded; SetInfo then fails, and the display driver's log line tells the two cases apart by that flag.
4. **On every mode change** (Enable and ReEnable) while `lpSetInfo` is known, the driver rebuilds the DDHALINFO and calls `SetInfo(&halinfo, TRUE)`.
5. **DestroyDriver** (in the DirectDraw callbacks, a 16-bit function in `vgpu98.drv`, without its CB32 flag): forgets `lpSetInfo`, returns DDHAL_DRIVER_HANDLED with DD_OK.

DD_VERSION stays 200h for every DirectX version; DD_HAL_VERSION 00FFh is the Windows 98 SE DDK's value (the DirectX 7 DDK's is 0100h).

**Without acceleration** (no register window, or a PROFILE without COMMANDS and BLIT), the DLL leaves the caps empty: DirectDraw emulates everything. WaitForVerticalBlank and GetScanLine need only the registers and are registered whenever BAR0 is mapped.

### VIDMEMINFO and the heap

| Offset | Field | Contents |
|---|---|---|
| 0 | fpPrimary | flat: the framebuffer's linear address (the primary surface is at video memory offset 0) |
| 4 | dwFlags | 0 |
| 8, 12 | dwDisplayWidth, dwDisplayHeight | the mode |
| 16 | lDisplayPitch | the mode's pitch |
| 20 | ddpfDisplay | DDPIXELFORMAT (32 bytes) of the mode |
| 52-68 | dwOffscreenAlign, dwOverlayAlign, dwTextureAlign, dwZBufferAlign, dwAlphaAlign | 16 bytes each |
| 72 | dwNumHeaps | 1 |
| 76 | pvmList | 16:16: one VIDMEM (24 bytes) |

The one heap is linear (VIDMEM_ISLINEAR) from the first 4 KB boundary after the primary frame to 256 KB below the top of video memory ([gpu-registers.md](gpu-registers.md)), inclusive end, usable for anything. DirectDraw allocates surfaces from it itself.

### Modes (DDHALMODEINFO)

`dwWidth`, `dwHeight`, `lPitch`, `dwBPP`, `wFlags` (DDMODEINFO_PALETTIZED at 8 bpp), `wRefreshRate` 0, and the RGB and alpha masks. The list holds every mode of the card's mode table at 8, 16 and 32 bpp that fits below the reserved top of video memory: the desktop modes and the low-resolution game modes (320×200, 320×240, 400×300, 512×384, 640×400). The display driver's ValidateMode applies the same limit, so on an 8 MB card 1920×1080 at 32 bpp (8,294,400 bytes, over 8 MB − 256 KB) is not offered ([modes.md](modes.md)). A mode's pitch is its width times its bytes per pixel, a multiple of 16 in every mode, so a flipping surface DirectDraw allocates at the display's width has the display's pitch (FLIP carries only a start address). DirectDraw sets modes through Windows' display-mode change, which reaches the driver's ReEnable; the driver must therefore accept every listed mode ([win98-display-driver.md](win98-display-driver.md)).

## The 32-bit DLL

- PE DLL linked by vglink: image base B00B0000h (in the shared system arena, the DDK's default for such DLLs), every section shared, Windows 4.0 subsystem. The entry point is a DllMain that returns TRUE. The export is the undecorated name `DriverInit`, for the stdcall function `_DriverInit@4`. It imports only from KERNEL32, by name.
- **Process model.** DriverInit runs in DDHELP. The callbacks run in whichever program's process calls DirectDraw, several programs at once if need be. All mutable state (contexts, texture handle tables, the fence counter, per-surface records, the pool's tables, DirectX 7's handles, palettes and state blocks, and the DLL's 24 MB heap for variable-size data) therefore lives in the DLL's shared sections or the shared block. Nothing may depend on a Win32 handle, a process heap or a critical section, none of which can be shared between processes on Windows 98.
- **The ring lock.** Every writer of the ring, and every caller that programs or resets it (the DLL, the Glide DLLs, and the 16-bit driver around a mode change), holds the ring lock: a dword that is 0 or 1, taken with `lock cmpxchg` by the DLL and `lock bts` by the 16-bit driver. A lock held by a process that has gone is released when the runtime calls ContextDestroyAll for that process. A process that used only DirectDraw never gets that call, so a waiter may also take the lock over: the DLL once it has been held for five seconds and neither FENCE nor RING_HEAD has moved in that time (never from the display driver), the display driver after about two seconds likewise, so a holder that is still working is never displaced (a hard failure in the guest is acceptable during development). When the DLL takes the lock over, or gives it back for a process that ended, what the holder wrote past the last doorbell is dropped unread (a packet may be half written: RING_TAIL never named it), and the GPU state epoch moves, so every context sends its whole state again (the GPU may hold part of the ended one's).
- **Log lines** go to BAR0's DEBUG register ([registers.md](registers.md)) through `driver32/logline.c`, which the Glide DLLs build in too ([glide.md](glide.md)): a format with `%s %c %d %u %x` (a width for the numbers) after an optional prefix copied as it is (none here: the DLL's formats start with its tag, `VGPU98 DLL <stamp>`), at most 159 characters, a newline added; a format ending in `%` stops there. The line is formatted first, then written whole under the shared block's `log_lock` (above), as DEBUG collects one line at a time for every writer. After a short spin (100,000 tries) the writer takes the lock over, writes its line and releases the lock, so a holder that died never leaves it held for good (its line is lost; one still writing may interleave with the new line). The one line saying the block is another build's goes under a lock word of the DLL's own; the DLL then drops the register window and writes nothing more.
- Every callback is `DWORD __stdcall Callback(LPDDHAL_xxxDATA)`, returning DDHAL_DRIVER_HANDLED (1) with a result in the data's `ddRVal`, or DDHAL_DRIVER_NOTHANDLED (0) to let DirectDraw do it.
- **While STATUS.HELD is set**, every callback that would use the GPU fails with DDERR_SURFACELOST. DrawPrimitives2 still applies the batch's state commands to its context (the runtime sends a state only when it changes, so one dropped would never come again) and skips only the drawing.
- **Callbacks that only test fences** (Flip, GetFlipStatus, GetBltStatus, a Lock without DDLOCK_WAIT) first restart a GPU that is neither running nor held, so a fence lost to a reset completes.
- **Where the ring is** (interface 2.1). At its first DriverInit with acceleration, the DLL takes the mini-VDD's buffer from the SYSBUF registers when PROFILE has SYSRING, the physical address is a multiple of 4 KB above the first megabyte, the linear one is in the shared or system arena (80000000h and up) and the size is a power of two from 1 MB to 4 MB ([gpu-registers.md](gpu-registers.md)): the ring is then the whole buffer in main memory, written through its linear address, and writing it costs no bus cycles. Otherwise the ring is 128 KB at the start of the GPU's reserve in video memory. The choice holds for every process (the DLL's sections are shared), and the debug log names it: `ring 2048 KB in main memory`, or `ring 128 KB in video memory (` the reason `)`. The largest packet is 64 KB either way. The first batch after the choice compares RING_BASE and RING_SIZE with it; if they differ (a GPU left running by an earlier load of the DLL), the GPU finishes what it has (while it runs, up to a second: NO_PROGRESS_MS, the OpenGL ICD's 5 seconds, below), is stopped, and starts on the chosen ring. A long batch rings the doorbell at least every 64 KB of packets, so the GPU starts on it before the batch ends. If the GPU refuses the buffer at RUN (STATUS.ERROR straight after), the DLL logs it and uses the ring in video memory from then on.
- **When RUN is clear and the GPU is not held** (the first use, or after a holder let go), the DLL programs the ring (RESET, FENCE written with the last value issued, RING_BASE, RING_SIZE, RUN) and marks every context to send its whole state again.
- **Packets the GPU refuses.** Every batch's fences (the last fence issued before it, and its own at its end) and the context it draws for go into a table of the last 32, under the ring lock, forgotten when the ring restarts. The context is named by a token: its handle and the serial number of its creation, so a batch of a context since destroyed never names the next context in the same slot; 0 is DirectDraw's own packets. The GPU stops on the refused packet, so the batch it stopped in is the oldest whose own fence FENCE has not reached (or the batch being written); one older than the table names no context. When the DLL finds the GPU stopped on an error, before it restarts the ring, it reads the refused packet back from the ring at ERROR_OFFSET (its header and first dword) and logs it with the context it was for: the first three of a kind (the error, the opcode, the first dword), and again after 10 seconds without one; the rest are counted in the report. A restart makes every context send its whole state again, so a bad state value would be refused for ever: when one context's same packet is refused three times, each within 2 seconds of the one before, the context **stops drawing** and the DLL says so once (a call that finds its context stopped by the restart it just made sends nothing either). A stopped context's DrawPrimitives2 calls still apply their state commands, as while the GPU is held, but send nothing and answer D3D_OK; its Clear and Clear2 send nothing. DirectDraw's own drawing and other contexts carry on, and a new context starts clean. A refused DirectDraw packet is never resent, so it cannot loop.
- **Every wait** (for a fence, ring space or idle) watches STATUS.ERROR, RUNNING and HELD, and gives up only when neither FENCE nor RING_HEAD has moved for a second (NO_PROGRESS_MS, 1000, and its lines' "a second", NO_PROGRESS_TEXT, unless the DLL's environment header defines them: this DLL and the Glide DLLs keep a second; the OpenGL ICD's `opengl/gpuenv.h` gives 5 seconds, as its device may spend over a second inside one packet making a pipeline cold: [opengl.md](opengl.md), Batches and the ring). On ERROR or no progress it recovers as [gpu-registers.md](gpu-registers.md) describes; when HELD it reports DDERR_SURFACELOST and leaves the GPU alone. A wait yields (`Sleep(0)`) for its first 20 ms and only then sleeps (`Sleep(1)`): a fence completes within a vertical blank, and Windows 98's `Sleep(1)` can take 5 ms. A wait whose fence is already complete returns before reading anything else, and a batch tries the ring lock before it reads a register or the clock. With the status page (interface 2.2), FENCE, RING_HEAD, STATUS and VBLANK_COUNT come from the GPU's status block in main memory: every check of a fence, a hold, ring room, a wait's progress and WaitForVerticalBlank's count costs no bus cycles ([gpu-registers.md](gpu-registers.md)). Every 256th look checks that the block's VBLANK_COUNT moved within 100 ms, and programs STATUS_BASE again if not. While it holds the lock, the DLL keeps a lower bound of the ring's free bytes (only the holder writes the ring, and the GPU only frees space): a packet that fits takes from it, and RING_HEAD is read only when it does not. The bound is forgotten whenever the lock is taken or the ring restarted.
- **The ring's second kind of client**. The Glide DLLs ([glide.md](glide.md)) drive the ring with this DLL's own code: `driver32/gpu.c` is built into each with `VGPU98_GLIDE_DLL`, which has it take `glide/gpuenv.h` in place of the DLL's header (the card's addresses as the Glide DLL found them, its log lines, with `ring:` for this DLL's tag, and its counters; this DLL's context hooks as a Glide DLL has them: its batches draw for no context, token 0). The lock, packets, fences, waits, the takeover after five seconds without progress, the recoveries and the doorbells are the same code under the same lock. This DLL's statics are shared by every process, a Glide DLL's are its process's, so what two instances must agree on lives in the shared block (the ring lock with its owner and time, the last fence issued, the ring's tail, the state epoch and owner) or the GPU's registers (RING_BASE, RING_SIZE, RING_TAIL, FENCE, STATUS, STATUS_BASE), never in an instance's statics alone:
  - every take of the lock reads RING_TAIL as the last doorbell, which the other kind of client may have rung since (this DLL's behaviour is otherwise unchanged); a takeover, and the release for a process that ended holding the lock, read it again before dropping what the holder wrote past it;
  - each instance chooses where the ring is by the same rule, from PROFILE and the SYSBUF registers (a Glide DLL at its first window's open), programs STATUS_BASE likewise, and checks RING_BASE and RING_SIZE against its choice at its first batch, moving a GPU that runs another ring as above;
  - a restart, or a batch abandoned, by either kind moves the state epoch: this DLL's contexts send their whole state again, a Glide DLL its registers as the device last had them ([glide.md](glide.md), Batches and the ring);
  - a Glide DLL whose process ends holding the lock (its DllMain's detach as the process ends) releases it as ContextDestroyAll does, what it wrote past the last doorbell dropped.

  The GPU refuses a Glide command only for its header ([gpu-commands.md](gpu-commands.md), Command set 2.4): the Glide device drops what it cannot take and goes on. A refusal in a Glide batch names no context.

### Tracking surfaces

DirectDraw gives each surface's global record a reserved dword for the driver. The DLL keeps there the fence after the last packet that used the surface: read, written, or shown. Lock, GetBltStatus and DestroySurface wait on it. A Direct3D batch gives its fence, while it still holds the ring lock, to its target and Z buffer and to every texture its draws used (a batch may change textures between draws), each with all its mip levels; not to a texture merely left bound (a Clear straight after a Flip would otherwise make it wait for a fence behind the flip). A batch that used more than 256 textures gives it to every texture (DirectX 7: every video memory surface with a handle of the context's DirectDraw local, levels and faces included). Flips are tracked by the fence the DLL issues straight after every FLIP. Every batch the DLL submits ends with a FENCE, and the shared block records the last value issued.

**Locks through copies in main memory**. With the pool and a GPU with PROFILE.DOWNLOAD (command set 2.3; 86Box's setting "Locks through main memory" On: [registers.md](registers.md)) and GPUVM, a Lock of a surface the GPU drew into (the flag above: back buffers, render-target textures, depth buffers) returns a pointer into a copy of the surface in the pool, so the program's CPU reads and writes main memory rather than the video memory window, where reads cost many times what writes do (GTA3's Trails read each finished frame back through it, about 95 ms a frame).
- **The Lock.** The copy holds the whole surface, laid out as video memory holds it from its offset (its pitch the surface's). DOWNLOAD ([gpu-commands.md](gpu-commands.md)) fills the Lock's rectangle, the whole surface without one, and the Lock waits for its fence; a GPU reset meanwhile (the shared block's `state_epoch` moved) leaves the copy unfilled, and the Lock fails with DDERR_SURFACELOST rather than hand it out. A DISCARDCONTENTS Lock reads nothing back once the copy was filled once (a new copy is filled first, so it never sends back another owner's bytes), and then waits only for the copy's last packet (an earlier Unlock's UPLOAD reading it; DDERR_WASSTILLDRAWING without DDLOCK_WAIT). The pointer is the rectangle's first pixel in the copy, or the surface's start without one; a DXT surface's rectangle must start at a block and is Locked in whole blocks.
- **The Unlock.** The surface's last Unlock sends the rectangle back with UPLOAD from the copy (its source at a GPU address), unless the Lock was READONLY, queued before any later packet, so a draw that samples the surface, or another DOWNLOAD of it, comes after; its fence becomes the surface's last use. Another Lock of the surface while one through its copy is open takes the usual path, and the copy goes back at the last of their Unlocks (DirectDraw's Unlock names no rectangle). An Unlock that cannot send the copy back (the GPU held, or the surface gone) is counted, and the first says so: `a Lock's writes through a copy in main memory were lost: the GPU took no UPLOAD (held, or the surface gone)`.
- **The copies.** A table shared by every process, behind its own lock, held for the table's records alone (never across the ring's lock, a wait or a pool call: blocks are made and freed outside it): 16 copies at most, each at most 4 MB and all of them at most 16 MB, the least lately used that no Lock holds going first. A copy is kept for its surface and reused Lock after Lock (made again when the surface needs more), and freed on the fence of the last packet that reads or writes it, at the latest when DestroySurface forgets the surface or the process that made it goes (it ended, or detached). A volume level (its slices past the copy's bytes) never takes one.
- **Texture writes**. A texture the GPU did not draw into, DISCARDCONTENTS-Locked for writing in 3 frames running (frames counted by FLIP and presenting blit; 32 textures followed), is written through its copy: once the copy was filled, nothing is read back, so its Lock waits for nothing but the copy's last UPLOAD, and the Unlock's UPLOAD comes after the queued draws that read the texture. Other texture Locks stay direct: GTA3's Trails texture, Locked whole without DISCARDCONTENTS each frame, costs about 8 ms a frame in writes through the window, where a DOWNLOAD would wait for the whole queue.
- **Fallbacks.** Without the pool, PROFILE.DOWNLOAD or GPUVM, for a surface over 4 MB, a volume level, a rectangle outside the surface, a DXT rectangle not at a block, a Lock while one through the same copy is open, or no entry or block to be had at once, a Lock takes the path above (SYNC, or the last-use fence), counted as without a copy.
- **The report** adds, while any: `locks through main memory:` n `of surfaces the GPU drew into,` n `of textures;` n `KB read back,` n `KB written back;` n `without a copy,` n `not sent back`.

### Execute buffers in the pool (interface 3.0)

Direct3D's vertex and command buffers are DirectDraw surfaces with DDSCAPS_EXECUTEBUFFER, which DirectDraw hands to the driver's execute-buffer callbacks (DDHALINFO's `lpDDExeBufCallbacks`; the same data as the surface callbacks) when it has them and the core caps list DDSCAPS_EXECUTEBUFFER (which Direct3D looks for: the DLL sets it with the pool). The DLL puts them in the **pool**, main memory the GPU reads through its page table ([gpu-registers.md](gpu-registers.md)), so the GPU reads vertices where the runtime or the program wrote them and the ring carries none of them.

- **The pool.** At its first DriverInit with 3D and PROFILE.GPUVM, the DLL asks the mini-VDD for its cap (DeviceIoControl POOL_QUERY on `\\.\VGPU98`, [minivdd.md](minivdd.md)); with a cap, it registers the callbacks and logs `pool of up to` the cap `in main memory`, otherwise `no pool:` and the reason, and DirectDraw keeps allocating execute buffers itself. Chunks come from the mini-VDD as buffers need them (POOL_GROW: 1 MB, or a larger buffer's size), in whatever process asks; they belong to the DLL as a whole (its sections are shared). While any Direct3D context exists (in any process), a chunk that becomes wholly free stays mapped for a while, so a game's buffers come and go without new allocations of locked pages: at most once a second, after a buffer is freed or at the end of a DrawPrimitives2 call (which also hands the mini-VDD what was queued to go back), a chunk with no buffer has its free blocks the GPU no longer reads merged, and is noted free (from then) when that leaves it one such block; one free for 10 seconds goes back (POOL_RELEASE, the longest free of those that can go first) while the chunks wholly free would still hold 2 MB without it, a chunk too large for that left for the smaller ones. Once none exists (the last context destroyed), each wholly free chunk goes back (POOL_RELEASE, once no queued packet reads it: the DLL waits for its fence first), but for one kept for the next buffers. A context counts while its process runs: the DX7 DDK has Windows 98 drivers leave ContextDestroyAll out, so the contexts of a process that ended without destroying them (it crashed) are freed with everything else of the process (its texture handles, DirectX 7 handles and palettes, the DLL's locks it held) when a context is created, or when DirectDraw destroys one of the process's buffers in another process (DDHELP cleaning up after it). Whether a process runs, `OpenProcess` and `GetExitCodeProcess` say (an ID that names no process is one that ended). A context is destroyed only in its own process or after that process ended, so a late ContextDestroy for an ended process's handle cannot destroy the context that took its slot since. A failed POOL_GROW is logged with the step the mini-VDD names (`the mini-VDD could not map` the size `more for the pool:` the step; the first three of each step, the report counting them all). Chunks are asked for in sizes of 1 MB, then 256 KB, then 64 KB, the next when one cannot be had (a larger buffer's own size if it is larger): small enough at the end that a game's buffers still fit while Windows is short of locked pages, large enough that a burst of them does not use up the mini-VDD's 256 chunk records; a size whose grow failed is not asked for again for a second. A context slot is claimed whole (compare and exchange), and one caller alone frees a context, so the count of contexts the pool keeps its chunks for never drifts. A handle to `\\.\VGPU98` is opened and closed for each request (they are rare, and a handle is its process's). The chunk, block and buffer tables are shared by every process, under a lock of their own that is never held across a request to the mini-VDD or a wait (a chunk being made is claimed first, and chunks leaving the pool are released after the lock is let go): a waiter yields, after 20 ms sleeps, and takes the lock over from a holder only after 2 seconds (a process that ended inside a callback); a process detaching gives back the locks it holds.
- **Blocks.** A buffer is one block of a chunk, 32-byte aligned: of the first 16 that fit on a list of the free blocks (most recently freed first), the one in the chunk whose buffers take the most bytes (each chunk counts them), so buffers gather in few chunks and the others empty; an allocation looks at free blocks alone, never at every buffer's. A freed block merges with a free neighbour only when both are ready or both still read by the GPU, so memory the GPU may still read never holds ready memory back; ready neighbours merge when an allocation passes them, and a chunk's free blocks all merge when it leaves the pool. A block freed (a buffer destroyed, or given fresh memory and its spares full) keeps the fence of the last batch that read it, and is handed out again only once that fence is complete (or the GPU is held: a hold comes with a RESET, which drops what was queued). When no chunk has room and no new chunk can be had, every buffer's spares go back to the pool first if together they could meet the request (below); failing that, an allocation waits for the earliest run of freed blocks that would fit (a freed block and the free ones after it); with none, a new buffer goes in system memory (fresh memory for a buffer in use, at a DISCARDCONTENTS Lock or a swap, comes from its spares (a Lock's) or the pool or not at all: the Lock or swap waits for the GPU instead; but a swap that asks for more than the buffer holds gets system memory, below). The chunk kept when chunks go back with no context left is one the GPU no longer reads before one it may, one of 1 MB before others, then the smallest.
- **System memory buffers.** The DDK has the driver allocate a buffer in system memory when it cannot place it where it prefers. A buffer the pool cannot hold (larger than the cap, or no chunk to be had) is memory the DLL allocates in the calling process (`VirtualAlloc`: reserved and committed, read and write), recorded with the pool's buffers and marked as theirs (DDRAWISURFGBL_SYSMEMEXECUTEBUFFER). The GPU never reads it: DrawPrimitives2 sends its vertices through the ring, read before the call returns, so its Locks never wait, and the runtime may swap or rewrite it at will. Destroying it frees the memory (`VirtualFree`) in its own process; in another (DirectDraw cleaning up after a process that ended) the memory went with the process. It moves into the pool the next time it may change memory, if a block can be had without waiting for the GPU: an application's vertex buffer at a Lock (a Lock may hand out a new pointer; its contents always go with it, DISCARDCONTENTS or not: draws during the Lock read them, and new memory never shows another buffer's bytes) or, not locked, before DrawPrimitives2 reads it (its contents copied: a static buffer is locked once; the old memory is kept until the buffer is destroyed, so a pointer the runtime kept from an earlier Lock still names memory), the runtime's own at a DrawPrimitives2 call that allows SWAPVERTEXBUFFER (fresh memory, as a swap gives; the command buffer, which only the DLL reads, stays). A try that finds no room keeps every buffer from trying again for a second. The program never sees an error; only those buffers cost more to draw. DDERR_OUTOFMEMORY is left for no memory at all or a full buffer table (16384 buffers).
- **Kinds,** from the surface's DDSCAPS2 bits: DDSCAPS2_VERTEXBUFFER an application's vertex buffer; DDSCAPS2_COMMANDBUFFER the runtime's command buffer, which only the DLL reads; neither, the runtime's own vertex buffer (or an execute buffer of the old execute-buffer API).

- **Versions.** Each buffer has the version of its contents, which STREAM carries ([gpu-commands.md](gpu-commands.md)): a new one at creation, at every Lock and Unlock but a read-only one, and with fresh memory; the runtime's own vertex buffers get a new one at every DrawPrimitives2 call that draws from them in place, and so does a buffer drawn from while still locked for writing (its Unlock not come yet), a DirectX 8 one under any write Lock and a DirectX 6 or 7 application vertex buffer under a NOOVERWRITE one, counted (under its other write Locks a DirectX 6 or 7 buffer is read from its contents from before the Lock, below, counted the same); a Lock's flags are recorded only when it hands out the memory (a Lock refused as still drawing leaves an open one's). Versions come from one counter in the shared block, so none is used twice for the same address, whatever process or buffer.
- **The contents from before a Lock** (DirectX 6 and 7). DirectX 6 and 7 draw no locked vertex buffer, so a draw that reaches the DLL while its application vertex buffer is locked for writing was issued before the Lock (the runtime sends it inside the program's Lock call, after the Lock was granted). Under a NOOVERWRITE Lock, which promises to leave what queued draws read, it reads in place under a new version, as before. Under any other write Lock it reads the buffer's contents from before the Lock. When the Lock gave the buffer fresh memory, the rename kept the old block instead of freeing it: the draw reads that block where it is, under its old version, and the batch's fence marks it. Otherwise the call's vertices go through the ring, copied during the call (the program writes under its Lock only once its Lock call returns). A rename while a Lock with a kept block is still open keeps that block, the contents from before the first Lock, and frees the newer one once read. At the Unlock the kept block becomes one of the buffer's spares (below), taken again only once the last batch that read it is done; with the buffer (Destroy, which also covers DirectDraw's clean-up after a process that ended) it goes back to the pool. A buffer once drawn while locked for writing other than with NOOVERWRITE is marked (copy-on-Lock): its later plain write Locks (neither DISCARDCONTENTS, NOOVERWRITE nor READONLY), busy or not, give it new memory with its contents copied, the old block kept as the contents from before the Lock however late the runtime sends its draws, for a buffer of up to 256 KB when a block can be had at once (its own spare, a free block or a new chunk, never one the GPU is still to finish with). Its idle DISCARDCONTENTS Locks keep its memory, and its busy ones rename as above, the old block kept. A NOOVERWRITE Lock (appending: the draws' vertices stay), a Lock while an earlier one is still open, a larger buffer, or no block to be had at once take the Lock as above: draws during it read in place under NOOVERWRITE, and through the ring otherwise. READONLY Locks, which write nothing, are read in place; DirectX 8 buffers are unchanged (their programs write first, then draw, with NOOVERWRITE). 3DMark99 and Giants drew from vertex buffers they were rewriting: the draw read the buffer's memory as it was, which a Lock without a rename let the game overwrite before the GPU read it, and after a DISCARDCONTENTS rename it read the new block while the old, which held its vertices, was freed.
- **A buffer's own spares**. A block a Lock's rename leaves stays its buffer's, as a spare: at most 2 a buffer, of at least the buffer's size (another goes back to the pool). The kept block becomes one at the Unlock. A rename at a Lock, of any DirectX version's vertex or index buffer, takes one of the buffer's spares of its size once no queued packet reads it, else a fresh block. A fresh block a Lock's rename takes always gets the buffer's current contents copied in, DISCARDCONTENTS or not, so no new memory shows another buffer's bytes; a spare taken for DISCARDCONTENTS keeps its own older vertices, one taken for a plain Lock gets the current contents. As on real hardware, where an idle DISCARDCONTENTS Lock returns the same memory and a busy one cycles among the buffer's own allocations, stale bytes a game draws are its own older vertices, in its own format. Spares go at Destroy, and every buffer's go back to the pool when an allocation finds no room and they together hold at least what it asks for. The runtime's own buffers' swaps, whose size changes, take no spare and take fresh memory uncopied (the runtime writes it before drawing).
- **The runtime's own vertex buffers** (and the old API's execute buffers) the runtime writes without a Lock, and may write again as soon as DrawPrimitives2 returns. The GPU reads a call's vertices from them in place only when the call allows SWAPVERTEXBUFFER. After any call that allows it (drawn or not, held or not), the buffer gets fresh memory whenever the GPU may still read the old or it is smaller than `dwReqVertexBufSize` (with REQVERTEXBUFSIZE, which the DDK has the driver honour; else its size), so the runtime fills that while the GPU reads the call's vertices, and the old memory goes once read; several buffers' worth thus rotate through the pool. When the pool cannot give the size asked for, the buffer goes in system memory (the DDK: a buffer too large for the driver's memory goes there), and one there moves into the pool when it has room, or grows. Without fresh memory the DLL waits until the GPU has read the call's vertices before it returns, and when the buffer cannot have the size asked for at all, SWAPVERTEXBUFFER and REQVERTEXBUFSIZE are cleared on return: the runtime is told there was no swap. A call without SWAPVERTEXBUFFER sends their vertices through the ring, read before it returns.
- **Diagnostics.** With the pool, the DLL's report adds three lines every 5 seconds while Direct3D works, one while any chunk has no buffer or one went back in those 5 seconds, and another while the runtime's own vertex buffers had windows or Locks: the pool against its cap, its chunks, and the live buffers of each kind with their sizes; the bytes the GPU was told to read from main memory (static application buffers, those locked with NOOVERWRITE or DISCARDCONTENTS, the runtime's) and the calls whose runtime buffer went through the ring; Locks of pool buffers (those that waited, those given fresh memory), swaps, and buffers refused; while any, `buffers renamed:` n `to their own spares,` n `to fresh blocks (`n `KB copied in);` n `spares given back for room`; `pool chunks without a buffer:` how many (their kilobytes), then `;` the kilobytes `given back` while contexts ran; `runtime buffers:` the windows DirectX 8 draws sent through the ring from the runtime's own vertex buffers in the pool (the bytes sent, a draw's byte offset into its stream included), the Locks of the runtime's own buffers in the pool by flag (DISCARDCONTENTS, NOOVERWRITE, other; a DirectX 7 program's buffers among them, whose draws send no window), and the windows checked again as each leaves a table of the last 32 (a sum of its first and last 64 bytes, in its own process, while its buffer has had no Lock that would wait or rename, DISCARDCONTENTS or one with neither NOOVERWRITE nor READONLY, and keeps its memory), those changed, and of those, those with a NOOVERWRITE Lock between. A change means the runtime rewrites what a GPU reading the buffer in place could still be reading; no change means something only with many windows checked, and says nothing of the runtime's buffers in system memory.

- **Vertices in the pool** (the surface `lpDDVertex` is a pool buffer, `dwVertexOffset` a multiple of 4; for the runtime's own buffers only with SWAPVERTEXBUFFER, above): STREAM 0 names the vertices where they are: the GPU address of `dwVertexOffset` and the buffer's bytes from there to its end, with the buffer's version; the batch's fence becomes the buffer's last use. Nothing of the vertices goes through the ring. The stream covers the whole rest of the buffer, not just the `dwVertexLength` vertices the call names: real hardware reads a vertex buffer itself, so a draw that reaches past the count its call names (a game that names too few) still finds its vertices there, and nothing outside the buffer is read; a vertex past the stream's end would read as 0. The report's figures for the bytes the GPU read count the calls' ranges. An application's vertex buffer locked for writing when the call comes (DirectX 6 and 7) is read in place under a new version when the Lock is NOOVERWRITE (which promises to leave what queued draws read), and otherwise from its contents from before the Lock: the block its Lock's rename kept, at that block's address and under its old version, the batch's fence marking that block instead; without a kept block, the call's vertices go through the ring ([Execute buffers in the pool](#execute-buffers-in-the-pool-interface-30)).
- **The vertex audit** (Diagnostics "DirectX 7: vertex audit", DEBUG's bit 1): each draw's furthest vertex (its start plus its count, or its base plus its largest index; the indices are read only for this) is checked against the vertices its call names (`dwVertexLength`) and the vertices the GPU can read from `dwVertexOffset` (the pool stream's; through the ring, a buffer of the DLL's to its end, user memory's and DirectDraw's own buffers' those the call names). A draw past the call's is counted and named ([registers.md](registers.md)); one past the GPU's reads vertices as 0 from the pool, and through the ring whatever the inline buffer still holds from earlier.
- **Other vertices** (user memory, a buffer in system memory) go to the GPU as its draws need them, byte for byte as the runtime holds them, with STREAM 0 over the inline buffer's vertex area (its first 15 MB, the call's stride). Of one of the DLL's buffers (in system memory, or the runtime's own without a swap) every vertex from `dwVertexOffset` to its end can go, as the pool's stream has them, and none past it; of user memory and DirectDraw's own buffers only the `dwVertexLength` the call names, the rest being memory whose size the driver does not know; at most 65536, and as many as the vertex area holds at the stride. Vertices go only up to the count the call names until one of its draws reaches past it, so a call within its count sends what it did before. Before each DRAW, the chunks of 64 vertices the draw touches (its indices, or its range) that the inline buffer does not hold yet in this call go there in INLINE packets, a dword at a time (`rep movsd`; never byte by byte, since with the ring in video memory every write is a bus write): the call's vertex *i* is at *i* times the stride. Inline vertices (the `_IMM` commands) go above the highest chunk of the call's own sent so far, or at the top of the vertex area; chunks of the call's that they overwrite are sent again when a later draw needs them.
- Inline vertices (the `_IMM` commands) always go through the inline buffer: when the call's vertices are in the pool, STREAM 0 moves to the inline buffer for such a draw and back for the next draw of the call's own. An indexed draw's indices go to the index area, and its DRAW names them from 0 with the command's wVStart as the base.
- **The render target by role**. Direct3D draws a flipping chain's frames into a back buffer, so when the context's target is the member of a primary flipping chain (one of its members is the primary surface) on display, whatever made ContextCreate, SetRenderTarget, SETRENDERTARGET or a handle's lookup find it, the DLL draws into the member attached to it, the one the next flip shows. A member is on display when its memory is the one the last FLIP showed (the shared block's `flip_start`, which a mode set returns to 0), or, when no member's memory is (walking the chain 16 members at most), when it is the front buffer. A DirectX 8 target moves at once, as DirectX 8 draws into no front buffer at all; an older interface's moves only once a FLIP came since the context saw it named (the shared block's `fence_flip` moved), so a loading screen drawn into the front buffer before any flip stays there. The target moved to keeps the flip count its first name had (a back buffer, it never moves again). It is applied at each DrawPrimitives2's start, before the check that the context is clean, and at each flush (a Clear's included; the flush judges whether the context was clean after it), so the CLEAR packets, the batch's fences, the flag Lock and Blt read for GPU writes and the TARGET packet all name the same member; a change makes the context unclean, so the target is described again. Every interface. A back buffer (the first or any other) is never moved, nor is a target outside a primary flipping chain (an off-screen surface, a texture, a windowed back buffer), nor the DLL's own copy of a DirectX 8 record ([Surface handles](#surface-handles)), which is no chain's member. GTA3 names its target once, and drew each frame into the buffer just flipped to the screen: the runtime named the front buffer, or a handle's lookup landed on it after an odd number of flips, and the display showed the frame being built.
- A draw command finds the GPU's state current when nothing changed since the context's last flush: the context is clean (no state, viewport or W-range command, SetRenderTarget, UPDATEPALETTE, SETPALETTE that changed something (a binding, a palette's flags, a palette recorded), texture handle destroyed or swapped, or flush without textures since), still owns the GPU's state, and the GPU was not reset meanwhile. It then sends no state at all, and the textures of the last flush are the batch's.
- **What a flush translates**: a whole flush (the GPU holds another context's state, or was reset) sends every render and stage state. Otherwise only the render states set since the last flush (a bit each, WRAP0's with WRAPU and WRAPV), and of each stage the states set since (ADDRESS's U and V with it); a stage is translated whole when a legacy render state was mapped onto it (TEXTUREMAPBLEND, the legacy filters and addressing), or blending now stops at it or stopped at it before, and its ALPHAOP when stage 0's texture alpha changed under the legacy MODULATE. A value sent only when it differs from what the GPU holds. The target and Z buffer are described again only when they, their memory or the world epoch changed since the last flush described them; the viewport and W range only after VIEWPORTINFO, WINFO, the defaults or an older interface's SetRenderTarget set them. A stage keeps its texture description (and an 8-bit DirectX 7 or 8 texture its palette), without looking its handle up, when the flush is not whole, no whole flush came since (a Clear's included), the last flush with textures completed and looked at the stage, the world epoch has not moved since (no surface, handle, colour key or attachment changed), no texture made every call unclean, the stage's texture handle was not set since (a flush without textures, a Clear, does not forget that), its texture's memory and source colour key are as they were, and an 8-bit DirectX 7 or 8 texture's palette is as sent (the palette epoch has not moved since, or the palette's version is the one the stage sent: below); the texture is still listed for the batch. Like the calls that keep their state, it has a window: a flush on another thread between AddAttachedSurface (which moves the world before DirectDraw links the level) and the link keeps the old chain until the world moves again. With no stage marked and neither the stage where blending stops nor stage 0's alpha changed, no stage is looked at. The `sent` line counts the descriptions kept.
- **Across calls** the context stays clean while nothing its last flush with textures was built from changed outside its state commands. A call starts unclean (its first draw checks everything) when the **world epoch**, one counter in the DLL, moved since that flush, or the target's, the Z buffer's or a stage texture's memory, or a texture's source colour key, differs from what the flush saw, or, once the palette epoch moved, a DirectX 7 or 8 stage's 8-bit texture's palette version from the one it sent (ctx_unchanged). The world epoch moves with every surface created, destroyed, lost or restored (DdCreateSurface and DdDestroySurface, which the DDK has DirectDraw call for both), every flip and FlipToGDISurface (a flip also moves DirectX 7 handles along a flipping chain), texture handle created, destroyed or swapped, DirectX 7 surface handle recorded or forgotten (CreateSurfaceEx, DestroyDDLocal), source colour key set (SetColorKey), surface attached (AddAttachedSurface) and process ended (its contexts and handles freed); a reset or mode change moves the GPU state epoch, which makes the next flush whole. SETPALETTE and UPDATEPALETTE leave the world epoch alone: palettes belong to the DirectDraw object, so another context's command changes them, and each has a version for the stages to compare instead ([DirectX 7 commands](#drawprimitives2s-directx-7-commands)). The **palette epoch**, a counter of its own, moves with every change of what a stage's palette is (a changed binding, changed flags, a palette made, UPDATEPALETTE, palettes forgotten); the flush and ctx_unchanged compare it first and look a stage's version up only when it moved (the flush reads it before the stages, so a change during the flush is seen at the next). A texture that makes every call of its context start unclean: an 8-bit one of an older interface's context (a DirectDraw palette, whose entries DirectDraw changes without telling the driver), and one with a level AddAttachedSurface attached (DeleteAttachedSurface takes it off without telling the driver; levels attached when the chain was made, DDAL_IMPLICIT, cannot be). A flush without textures (a Clear) leaves the context clean if it was, the GPU held its state, and the flush sent no state value (without the textures, the stage values that depend on them are guesses). The report counts the calls whose first draw kept the state.
- A flush builds a stage's TEXTURE packet from DirectDraw's surface records only when it has none cached for the texture handle (4,096 kept, in sets of eight chosen by the handle and its scope, the DirectX 7 DirectDraw object; the least recently used of a set replaced; an entry holds 4 + 3 × 9 dwords at most, a volume's description, which a 2D texture's (4 + 2 × 12) fits, the cache under 1 MB; a cube map's is built at each use and not kept, the entry its handle had cleared, as is any description too long for an entry, each listed for the batch once) or something it was built from changed: the handle's surface, the top level's memory, its source colour key, its palette (DirectX 6: DirectDraw's palette object) and the palette's alpha flag (DirectX 7 and 8: that flag alone, so a texture bound to another palette keeps its description), the DLL's surface epoch (moved by every CreateSurface, DestroySurface and texture handle created, destroyed or swapped; for a DirectX 7 surface handle, the handle's generation instead), the GPU's state epoch (every reset and mode change), and the mip chain: a cached description is used only while walking the attachments still finds the same levels (a level attached or detached anywhere: the driver is told of AddAttachedSurface, never of DeleteAttachedSurface). An 8-bit texture's palette goes by its colours' signature with DirectX 6, the entries read at every flush, and by its version with DirectX 7 and 8 (PAL_UNBOUND when none is bound or recorded), the one read with the description's alpha flag: the entries are read, and PALETTE sent, only when the version differs from the one the stage sent. The declaration honours the texture-coordinate-size bits a DirectX 7 runtime may set: each set is declared with its 1-4 components, and the GPU pads it ((u) reads as (u, 1, 0, 0), as in the reference rasterizer).
- A DRAW's edge flags always fit in one packet (a command counts its primitives in 16 bits); its indices go first into the index area in INLINE packets of at most 64 KB.
- The DLL sends a stage's texture (TEXTURE, and PALETTE for P8) when a texture handle is set, and again when the surface or its palette changes.

### Render states

The DLL passes most Direct3D render states through ([gpu-commands.md](gpu-commands.md)), reducing values as Direct3D defines before the GPU sees them: ALPHAREF to its low 8 bits (as the reference rasterizer does; DirectX 6.1's headers still type it as a fixed-point value), ZBIAS clamped to 16, MAXANISOTROPY clamped to 16, TEXCOORDINDEX to its coordinate set and DirectX 7's coordinate generation (bits 0-2 and 16-17), TEXTURETRANSFORMFLAGS to its count and PROJECTED, WRAPn to its four coordinates (DirectX 7), the material sources to 0-2 and FOGVERTEXMODE and VERTEXBLEND to 0-3. A DirectX 7 context starts at DirectX 7's defaults: CLIPPING, LIGHTING, COLORVERTEX and LOCALVIEWER on, the diffuse, specular and ambient material sources COLOR1, COLOR2 and COLOR2.

It translates the DirectX 5 states that act on texture stage 0, as the reference rasterizer does:

| Direct3D state | Becomes |
|---|---|
| TEXTUREHANDLE (1) | stage 0's texture |
| TEXTUREMAPBLEND (21) | stage 0 (and 1) colour and alpha operations, per legacy blend mode. Several modes depend on whether the bound texture has alpha (MODULATE takes alpha from the texture if it has any, else from the diffuse colour), so the mapping is redone whenever the bound texture changes |
| TEXTUREMAG (17), TEXTUREMIN (18) | stage 0's MAGFILTER, MINFILTER and MIPFILTER, with anisotropic filtering when ANISOTROPY is above 1 |
| TEXTUREADDRESS (3), TEXTUREADDRESSU (44), TEXTUREADDRESSV (45) | stage 0's ADDRESSU and ADDRESSV |
| BORDERCOLOR (43), MIPMAPLODBIAS (46), ANISOTROPY (49) | stage 0's BORDERCOLOR, MIPMAPLODBIAS, MAXANISOTROPY |
| WRAPU (5), WRAPV (6) | WRAP0 |
| TSS ADDRESS (12) | ADDRESSU and ADDRESSV |

Every value Direct3D defines is mapped onto one the GPU accepts, so a program can never stop the GPU:

- Magnification filters the caps do not advertise (flat and Gaussian cubic) become linear.
- SHADEMODE phong goes through: the GPU draws it as Gouraud.
- A colour-only operation (18-21, 24) given as an ALPHAOP is reported by ValidateTextureStageState (D3DERR_UNSUPPORTEDALPHAOPERATION) and sent as SELECTARG1.
- A texture argument selector Direct3D does not define (above specular, 4) is reported by ValidateTextureStageState and sent as "current".
- The stages that blend are counted as the reference rasterizer counts them (`UpdateActiveTexStageCount`): one while the legacy TEXTUREHANDLE is set; otherwise up to the first stage whose COLOROP is DISABLE, or that has no texture and takes COLORARG1 from the texture. That stage is sent with COLOROP DISABLE, so untextured geometry shows its diffuse colour.
- States the caps do not advertise and that change nothing on this GPU are recorded and otherwise dropped: ANTIALIAS, LINEPATTERN, MONOENABLE, ROP2, PLANEMASK, ZVISIBLE, SUBPIXEL, SUBPIXELX, STIPPLEDALPHA, STIPPLEENABLE, EDGEANTIALIAS, FLUSHBATCH, TRANSLUCENTSORTINDEPENDENT, STIPPLEPATTERN00-31.

## The DirectX 7 interface

A DirectX 7 (or later) runtime finds D3DDEVCAPS_DRAWPRIMITIVES2EX in the device caps ([d3d-caps.md](d3d-caps.md)) and asks GetDriverInfo for the Miscellaneous2 callbacks; from then on it drives the card through the DirectX 7 interface, for every program and every Direct3D interface version. The stock DirectX 6.1 runtime knows neither and keeps the DirectX 6 interface above. The DLL takes the request for the Miscellaneous2 callbacks as the sign (`d3d7_on`, for every process: the runtime is the system's) and logs `the DirectX 7 driver interface` once.

The DLL's tables for it are shared by every process, each under a lock of its own (the pool's kind: held only for table work, taken over after 2 seconds from a process that ended inside a callback). Variable-size data (palettes, recorded state blocks, light tables) lives in the DLL's own heap, 24 MB in its shared data. Its allocator keeps the free blocks on lists by size, two levels (the size's power of two, then eight steps within it), with a bitmap of the lists that hold any, over blocks with a 16-byte header (their size, whether in use, the size of the block before): an allocation takes the first block of its size's own list when that fits (a hole of its size used again), else the first block of the first list whose every block fits, else (none) the first block of its own list that fits, splitting off the rest when it holds a block (32 bytes), and a freed block merges with free neighbours on both sides, so an allocation costs the same however many blocks the heap holds (the first fit from a low mark before walked more of them as they grew). A free of a block not in use is ignored. The DLL wraps it with its lock and its line when no block fits (`the DLL's heap has no` n `bytes left`). The allocator (`heapcore.c`) is plain C with no Windows types: the suite builds it on the host, and its `heap_allocator` test makes random allocations and frees, checking the heap whole as it goes (the blocks tile it, no two free ones touch, every free block on its size's list), every block's bytes its own, exhaustion and a double free.

### Surface handles

The runtime names surfaces in the command stream by handles: small integers it assigns per DirectDraw local object (one per DirectDraw object of a process), 0 never valid, kept in each surface's `lpSurfMore->dwSurfaceHandle` (DDRAWI_DDRAWSURFACE_MORE offset 100; the local object is at offset 8).

- **CreateSurfaceEx** (after DirectDraw created surfaces, in video or system memory, or restored lost ones): the DLL walks the root it is given and everything attached, and records as (local, handle) to surface those a command can name: a texture's top level or a cube map's root, render targets (DDSCAPS_3DDEVICE: a flipping chain's buffers each hold a handle of their own, and so may a mip level or cube face that can be a target), Z buffers. A texture's other levels and faces are reached through their root at use (DirectX 8's copies record them too, below). Execute buffers are recorded only as DirectX 8's vertex and index buffers ([Vertex and index buffers](#vertex-and-index-buffers)); the runtime's command buffers never (no command names them). A system memory surface given without memory (`fpVidMem` 0) is being destroyed: its handle is forgotten. A video memory surface without memory is ignored (DestroySurface forgets it). Two surfaces whose handles the runtime swapped (CREATESURFACEEX_SWAPHANDLES) come in two calls, each recorded under the handle it now holds. The call fails with DDERR_OUTOFMEMORY only when the table is full; a system memory surface in a format the card lacks is still recorded (it may be meant for DirectDraw's emulation).
- **DirectX 8's resources: the DLL's own copies**. The DirectX 8 runtime's records of the resources it makes for a device (textures, vertex and index buffers, render targets and depth buffers made after the device) live for one call: it reuses them at once. On a DirectDraw local object a DirectX 8 context was made on (marked at its ContextCreate, in its process; the DirectX 8.1 runtime gives no DXVERSION), CreateSurfaceEx therefore copies the root and everything attached into one block of the DLL's heap (24 MB), in DirectDraw's own structure shapes: each surface's local, global and "more" records (size, pitch, format, caps and caps2, colour keys, the memory: a video memory address or the process's own system memory, the handle, the local object), the attachments rebuilt between the copies in the runtime's order with their flags, the pointers the DLL never follows cleared; a level in video memory of a volume gets its slice pitch and the slices flag. Every copy with a handle is recorded (levels and faces too: a Lock or a destroy notice names them; the runtime's command buffers never), and the block goes with its last handle. A level announced again on its own keeps its copy in its chain's block; a handle recorded again into a new block gets the last fence issued, and the GPU-writes flag of its old copy of the same memory (not a buffer's: the pool keeps buffers' fences). What the device's creation made before its context (the flipping chain, its Z buffer), the flipping chain always, and the runtime's own vertex and command buffers in the pool keep the runtime's records, which last. An application's vertex or index buffer in the pool is copied too (the runtime reuses those records as well): at CreateSurfaceEx the pool's buffer record takes a global record of its own, its memory and size from the pool's record, its flags and format from the runtime's, its dwReserved1 the pool's index, and the copy points at it; the pool writes the buffer's moves there, never into the runtime's record, which a Lock (its record valid for the call) is told the buffer's memory and size, and a destroy clears. Adoption takes the buffer CreateExecuteBuffer made with that record (at the memory it gave it), or the one whose index and memory the record carries; a handle recorded again keeps its buffer's own record (found by its copy, then in the table). A buffer a call names by the runtime's record is found, in a process with a DirectX 8 context on the object, by its handle's copy (the process's own buffer); then by the index in the record (a buffer not adopted); then among the adopted buffers by its DirectDraw object and handle (the calling process's, else one a process that ended left: DDHELP destroying it; one whose handle the map dropped first); then by the index and the memory the record holds (a destroy notice without the handle). The runtime's own vertex and command buffers and DirectDraw's own are found by the index alone, DirectX 7's by the index (the later steps find nothing of theirs). A destroy forgets an adopted buffer's handle by the buffer (its object, handle and copy), not by the call's record. A surface DirectDraw's callbacks receive (Lock, Blt, DestroySurface, GetBltStatus, Flip) is matched to its record by its local object and handle: the fence and the GPU-writes flag read and written are the record's. A DirectX 8 context takes the copies of its target and Z buffer when the map holds them (one made before the object was marked, a windowed back buffer or the device's Z buffer, is copied at ContextCreate from the call's own records: only the flipping chain keeps the runtime's), and at each DrawPrimitives2 after the world epoch moved looks a copied one up again by its handle (its surface may have gone); copies dropped in bulk (DestroyDDLocal, a process's end) first wait for the last fence issued. A tree the heap has no room for is not recorded: logged (the first three), counted, the handle's earlier record dropped, and the call fails with DDERR_OUTOFMEMORY. A DirectX 8 mark an ended process left on an object's address is taken over by the next process to make a DirectX 8 context there, and the ended process's handles under it go.
- **Flips** move memory, handles and the driver's reserved fields together around a flipping chain, so a handle keeps naming the same memory. A lookup checks that the recorded surface still holds the handle, else follows the chain (its DDSCAPS_FLIP attachments; an attached Z buffer is not one) to the buffer that does, and remembers it.
- **DestroySurface** (video memory: lost or destroyed) forgets the surface's handle. A lost surface comes back under the same handle through CreateSurfaceEx.
- **DestroyDDLocal** forgets every handle and palette of the local object; **ContextDestroyAll** those its process recorded.
- The map holds 131071 handles in all (DirectX 8's vertex and index buffers, and its copies' levels and faces, have handles too): an open-addressed hash of the local object and the handle, where a deleted entry pulls the later ones of its run back, so lookups stay short. Each entry has a generation, new whenever its handle names another surface; it keys the texture description cache for DirectX 7 handles (DirectX 6 handles keep the surface epoch).

### Contexts

ContextCreate gives the DirectDraw local object (in `lpDDGbl`'s place) and the target and Z buffer as surface local objects (in place of their interfaces). The context keeps the local object and the two handles, resolves them to the surfaces holding them when they are named (ContextCreate, SETRENDERTARGET), and then keeps those surface objects: a flip moves handles and memory together, and the runtime names the back buffer by the handle it then holds (the DDK's "D3dCreateSurfaceEx Handles and Flip"), which the surface object follows whether or not the runtime names it again. Textures are looked up by handle at every use. The texture stage states' TEXTUREMAP (and the legacy TEXTUREHANDLE render state) are surface handles of the textures' top levels. A DirectX 7 driver gets no TextureCreate, SetRenderTarget, Clear or Clear2 calls from the runtime as far as the DDK's samples show (the Permedia 2 sample has none); the reference rasterizer still takes them for a context of an older interface (ContextCreate's `dwhContext`, an input, names the interface: 3 the DirectX 7 one, 2 and below older ones), so the DLL keeps them for that case: a context the runtime calls TextureCreate for names its textures by those handles from then on; SetRenderTarget takes interface pointers (local objects for the DirectX 7 interface's own contexts), records the new surfaces' handles, and makes the viewport the whole target for an older interface's context (DirectX 7's keeps it); TextureDestroy unbinds the handle only from contexts that use TextureCreate's handles.

A DirectX 7 context also keeps the transform and lighting state the GPU takes ([gpu-commands.md](gpu-commands.md)): the matrices by the GPU's TRANSFORM numbers, a light table, the material, six clip planes and the Z range, each sent when it changed (and all of it after a reset or when another context drew last). Its render states start at Direct3D 7's defaults (CLIPPING, LIGHTING, COLORVERTEX and LOCALVIEWER on; the material sources COLOR1, COLOR2, COLOR2, MATERIAL), its matrices at the identity, the Z range at 0-1.

Any command that runs past the end of the command buffer (`dwCommandLength`; with the old execute-buffer API its counts are the program's) stops the call with D3DERR_COMMAND_UNPARSED and its offset, as an unknown one does; so does an inline-vertex command when the call's vertex format is not one the GPU takes, since its vertices cannot be stepped over. An infinite far value fogs by W, as the reference rasterizer does for any range but (1, 1), and a refused range fogs by the range kept. An older 86Box refuses an infinite far value, so the DLL and the card should come from one release. A draw without a usable target (none, or one in a format the GPU cannot draw into) is skipped; the call's other commands still count, and a later SETRENDERTARGET may make drawing possible again.

- **Lights.** The table holds every light the program created, enabled or not. A flush gives the GPU's eight slots the enabled lights in table order, of the types the caps advertise (point, spot, directional): a PARALLELPOINT light (type 4), which DirectX 7 still defines but no caps advertise, and lights past the eighth stay out. LIGHTENABLE names the slots in use.
- **Vertex formats.** Besides XYZRHW, the transform and lighting device sends untransformed vertices: XYZ, or XYZB1-5 with 1-5 blending weights after the position (declared as BLENDWEIGHT of up to four floats: the transform uses at most three), a normal, D3DLVERTEX's reserved dword, the colours and the coordinate sets. They take the GPU's transform program.
- **State blocks.** Between STATESETBEGIN and STATESETEND the state commands (render and stage states, viewport, W and Z ranges, material, CREATELIGHT, SETLIGHT, transforms, clip planes, EXT) are recorded into the block, as sent, instead of being applied; STATESETEXECUTE replays them; STATESETCAPTURE writes the context's current values into them; STATESETDELETE frees the block. Blocks belong to their context and go with it (1024 in all). A BEGIN that finds no room still takes the block's commands, into nothing, rather than apply them. This is what the reference rasterizer does.
- **TEXBLT** copies a rectangle of the source texture (in its top level's coordinates) to a point of the destination (in its top level's), for every level the two share, the rectangle and point halved at each level; when the destination's top level is smaller than the source's, the source's levels start at the one of its size (each dimension halved down to 1). For cube maps, the faces dwFlags names (all six when none): one face takes the rectangle and point as a texture does, two or more are copied whole. From a texture in video memory, a BLT per level (DXT ones in whole blocks); from one in system memory, an UPLOAD per level with the texels inline. Both must have the same format (the runtime sees to it). A destination handle of 0 (preload a managed texture) does nothing. The GPU runs them in order with the drawing, so no wait is needed; the destination, and a source in video memory, get the batch's fence with all their levels and faces.

### System-to-video blits

With DDCAPS_CANBLTSYSMEM in the core caps (`dwSVBCaps` DDCAPS_BLT, `dwSVBRops` SRCCOPY, no SVB colour key or effect caps), DirectDraw sends Blt every blit from a system memory surface to video memory that those caps allow, and does colour-keyed and stretched ones in its emulation. The DLL takes copies of the same size with raster operation SRCCOPY (or none) and only the flags WAIT, ASYNC or DONOTWAIT: in the same format (not DXT, which DirectDraw copies itself without DDCAPS2_COPYFOURCC), or from a DXT surface to a 16- or 32-bit colour format (R5G6B5, X1R5G5B5, A1R5G5B5, A4R4G4B4, X8R8G8B8, A8R8G8B8) at most 4096 texels wide, decompressed in the DLL exactly as the GPU decodes DXT ([gpu-formats.md](gpu-formats.md); DXT2 and DXT4 keep their premultiplied colours). The DirectX 7 DDK lets such a driver refuse decompression, but DirectDraw's emulation did it before these caps, so the DLL keeps it. Each destination rectangle's rows go as UPLOAD packets with the texels inline (no wait: the bytes are in the ring before Blt returns), and the destination gets the fence. Anything else is NOTHANDLED, which DirectDraw reports as DDERR_UNSUPPORTED.

### GetDriverState, DestroyDDLocal

GetDriverState answers NOTHANDLED with DDERR_UNSUPPORTED (no statistics are kept: the runtime's GetInfo fails). DestroyDDLocal forgets the local object's handles and palettes.

## The DirectX 8 interface

A DirectX 8 runtime asks the driver for GetDriverInfo2; a driver that answers it is a DirectX 8 driver, and the runtime then drives it through DirectX 8's own interface for DirectX 8 programs (streams, index buffers, shader handles, DirectX 8's states and formats), and through the DirectX 7 interface above for older ones. The DLL answers only with the GPU's PROFILE.FIXED8 (command set 2.1, [gpu-commands.md](gpu-commands.md)); without it (the setting "DirectX 8 interface" Off, or a 2.0 GPU) the runtime finds a DirectX 7 driver and drives DirectX 8 programs through its compatibility layer. The facts are restated from the Windows XP DDK's DirectX 8.1 driver interface (`d3dhal.h`, `ddrawi.h`, its documentation), the DirectX 8.1 SDK's headers and documentation, and the DDK's Permedia 3 sample with its Windows 98 build, read for facts only (archive note 11). The DLL's DirectX 8 parts are `d3d8.c` (the query, caps, formats, vertex shaders) and DrawPrimitives2's DirectX 8 commands in `dp2.c`.

### GetDriverInfo2

- **Opting in.** DDHALINFO's `dwFlags` must carry DDHALINFO_GETDRIVERINFO2 (8h). The 16-bit driver builds DDHALINFO; the DLL asks for the flag through the shared block's `hal_flags` (written at DriverInit, which runs first), and the display driver ORs it in with GETDRIVERINFOSET. A display driver of an older build ignores the field, so it never offers DirectX 8.
- **The request** comes through GetDriverInfo with GUID_DDStereoMode (F828169C-A8E8-11D2-A1F2-00A0C983EAF6), which GetDriverInfo2 shares: its data is a DD_GETDRIVERINFO2DATA (dwReserved, dwMagic, dwType, dwExpectedSize) when the dword at offset 4 is FFFFFFFFh, else a stereo-mode query, which stays unanswered (DDERR_CURRENTLYNOTAVAIL). The size to honour is the header's dwExpectedSize, not GetDriverInfo's; the answer goes into the same buffer.

| dwType | Answer |
|---|---|
| 1 GETD3DCAPS8 | D3DCAPS8 (212 bytes, [d3d-caps.md](d3d-caps.md)), at most dwExpectedSize bytes, over the header; `dwActualSize` the bytes written; logged once (`the DirectX 8 driver interface`) |
| 2 GETFORMATCOUNT | DD_GETFORMATCOUNTDATA's dwFormatCount: the format list's entries (24 bytes) |
| 3 GETFORMAT | DD_GETFORMATDATA: entry dwFormatIndex as a whole DDPIXELFORMAT (52 bytes): DDPF_D3DFORMAT, the D3DFORMAT code in dwFourCC, its operations in dwRBitMask (a DirectX 9 runtime's version in dwSize is overwritten) |
| 4 DXVERSION | The application runtime's version is noted (logged when it changes) and answered (24 bytes) |
| others (DirectX 9's 10h-23h) | DDERR_CURRENTLYNOTAVAIL |

Every answer returns HANDLED. GUID_DDMoreSurfaceCaps adds DDSCAPS2_VOLUME to its caps with the DirectX 8 interface.

### Contexts

ContextCreate's `dwhContext` names the creating interface on the way in: 4 is DirectX 8's. Such a context (with PROFILE.FIXED8) is a **DirectX 8 context**: DirectX 8's render states 153-173 and stage states 25-28 are its own (an older context's are ignored, and stay at DirectX 8's defaults, which every context sends a FIXED8 GPU: the GPU holds one state), its filters are DirectX 8's numbers (D3DTEXF: none 0, point 1, linear 2, anisotropic 3, flat cubic 4, Gaussian cubic 5, one numbering for MAGFILTER, MINFILTER and MIPFILTER), translated into DirectX 7's as the GPU takes them (cubic magnification as linear; MIPFILTER none 0 its default), its world matrices are numbered 256 + n (world matrices 0-3 the GPU's 0-3, 4-255 the palette, kept in the DLL's heap from the first one set and sent as TRANSFORM 256 + n; a never-set one is the identity), VERTEXBLEND takes 255 and 256, and it may use TOP 25-26, the TEMP argument and RESULTARG. Render state 153 (SOFTWAREVERTEXPROCESSING), 165 and 169 are recorded and never sent. ValidateTextureStageState takes DirectX 8's operations, arguments (TEMP, the third argument of MULTIPLYADD and LERP) and RESULTARG (current or temp) for such a context. The palette is sent whole (to the highest matrix either set, never-set ones as the identity) when another context's is on the GPU (a context, not its slot, which a later context may reuse), else what changed.

### Vertex and index buffers

DirectX 8's vertex and index buffers are execute buffers in the pool, as DirectX 7's vertex buffers are ([Execute buffers in the pool](#execute-buffers-in-the-pool-interface-30)): an index buffer (DDSCAPS2_INDEXBUFFER) is a kind of its own, PB_INDEX, locked, versioned and moved into the pool as an application's vertex buffer. With the pool, D3DCAPS8 has D3DDEVCAPS_HWVERTEXBUFFER and HWINDEXBUFFER, so the runtime asks the driver for them. Every DirectX 8 buffer, system memory ones included, gets a handle at CreateSurfaceEx: the handle map records them apart from textures and targets, moving a buffer epoch of its own rather than the world epoch (nothing a context's flush builds names them), and forgets one when DestroyExecuteBuffer destroys it (or CreateSurfaceEx says a system memory one is going). Windows 98 keeps a DirectDraw-allocated buffer's size in `lPitch`.

### Vertex shaders

SETVERTEXSHADER names the vertex input of stream 0's data, or of every stream: a handle with bit 0 clear is an **FVF code**, a declaration of stream 0 as DirectX 7's are (above), with DirectX 8's additions: D3DFVF_PSIZE (DirectX 7's reserved dword, in the same place) as the PSIZE element, and with D3DFVF_LASTBETA_UBYTE4, or while INDEXEDVERTEXBLENDENABLE is on, the last weight dword as BLENDINDICES (UBYTE4) (the DirectX 8 SDK has the matrix indices right after the last weight whenever indexed blending is on; a draw after the state changed makes the declaration again); a handle with bit 0 set is a **shader** CREATEVERTEXSHADER made. The context keeps its shaders in the DLL's heap: one with a function (dwCodeSize not 0) is a programmable shader, translated into a vertex program ([Shaders](#shaders)) with PROFILE.PROGRAMS and kept as unusable without it (no shaders offered then); a declaration-only one (DirectX 8's fixed function with a declaration: tweening, several streams) becomes DECLARE elements. Its tokens: STREAM selects a stream (the tessellator's makes it unusable), STREAMDATA loads a register at the offset the stream's tokens before it reach (skips counted in dwords), CONSTMEM and EXT are stepped over, TESSELLATOR makes it unusable, END ends it. The registers are POSITION (0), BLENDWEIGHT (1), BLENDINDICES (2), NORMAL (3), PSIZE (4), DIFFUSE and SPECULAR (5, 6: COLOR 0 and 1), TEXCOORD0-7 (7-14), POSITION2 and NORMAL2 (15, 16: index 1); the GPU's element type is DirectX 8's plus one. A declaration the GPU's fixed function cannot read (no untransformed position, a use twice, a type its use does not take: [gpu-commands.md](gpu-commands.md), DECLARE), or with an element reaching past MaxStreamStride (256 bytes), is unusable too: its draws are skipped and counted, never refused by the GPU.

### Shaders

With the GPU's PROFILE.PROGRAMS (command set 2.2, [gpu-commands.md](gpu-commands.md)) and the DirectX 8 interface, D3DCAPS8 offers vertex shaders 1.1 and pixel shaders 1.4 ([d3d-caps.md](d3d-caps.md)), and the DLL translates every shader a program makes into the GPU's programs. The rules below are the DirectX 8.1 SDK's shader reference and the DDKs' token pages, restated. The translator (`xlate.c`) is plain C with no Windows types: the suite compiles it on the host and runs its output through the GPU's own validator (`card/vid_vgpu98_prog.h`).

**Shaders and programs.**
- **Ids.** A pixel shader, and a vertex shader with a function, get a GPU program id (1-4095) at creation, from one table every process shares; deletion and the context's end give it back. A declaration-only vertex shader is the fixed function and gets none.
- **Creation.** CREATEPIXELSHADER and CREATEVERTEXSHADER translate the shader at once (its PROGRAM goes with the first draw that binds it, and again whenever a reset has cost the GPU its programs). The runtime has validated the tokens for their version (and flushed); the translator checks what it relies on (the version token, the tokens' bounds, opcodes and registers it knows, at most 256 instructions once lowered). A shader it cannot take, or one with no id or heap room left, fails DrawPrimitives2: D3DERR_DRIVERINVALIDCALL in `ddrval`, the command's offset in `dwErrorOffset`, so the runtime fails the program's call (the DDK: creation is synchronous and reported by failing the call). A device "should never fail" a valid shader up to the version it reports, so nothing the caps offer is refused for want of support.
- **Binding.** SETPIXELSHADER and SETVERTEXSHADER pick the programs; the next draw sends BIND when the GPU holds another pair. Pixel and vertex shaders are independent: an FVF code or a declaration-only shader is the fixed-function vertex side (BIND's vertex 0), pixel shader 0 the fixed-function pixel side.
- **Constants.** The context keeps 192 vertex and 8 pixel constants. SETVERTEXSHADERCONST and SETPIXELSHADERCONST write them; they are state commands (recorded in state blocks, applied at EXECUTE, taken at CAPTURE). At SETVERTEXSHADER the shader's declaration constants (CONSTMEM) are written over them, and at SETPIXELSHADER a pixel shader's def constants, if the runtime left any in its code: the DDK's rule that a shader's own constants load whenever it is set, the others keeping their values. The next draw with a program of the kind sends CONSTANTS for the registers that changed since the GPU last held this context's; after another context's (or a reset), every one: the context's vertex constants up to the highest it set, zeros above them up to the highest the GPU may hold, all 8 pixel constants.
- **Textures.** With a pixel shader bound, the flush sends the texture and palette of every stage its program samples (the program's STAGE operands), whatever their COLOROP: DirectX 8's default COLOROP of stages 1-7 is DISABLE, which a shader does not change and the fixed function stops at.
- **Leaving a shader** is BIND 0 for that side: the stage, transform, light and material states a program set aside are the GPU's still, since the DLL sends them whatever is bound (DirectX 8 preserves them across shaders).
- **Deletion** gives back the program's id (a bound one is unbound by its next draw's BIND); the GPU keeps the old program until the id's next owner sends its own, which replaces it (the DLL sends no free: the GPU holds at most 4095).
- **State blocks** record SETPIXELSHADER and both constant commands as they record SETVERTEXSHADER, and CAPTURE writes their current values (handles and constants).

**Pixel shaders.** Registers: ps 1.0-1.3's r0 and r1 are TEMP 0 and 1, t0-t3 TEMP 2-5; ps 1.4's r0-r5 are TEMP 0-5 and t0-t5 COORD 0-5 (its texture coordinate registers); c0-c7 are CONST 0-7, v0 and v1 INPUT 0 and 1; TEMP 6-15 are the translator's scratch. The program's colour is TEMP 0. Its range is the caps' MaxPixelShaderValue. Writes that hold texture coordinates, not register values a shader reads, carry NOCLAMP: the pad instructions' dot products, the scratch S and S2, BEM's coordinates (DirectX 8 computes those coordinates beyond the registers' range).
- **Arithmetic** keeps its form: add, sub, mul, mad, lrp, mov, dp3, dp4, cnd, cmp become ADD, SUB, MUL, MAD, LRP, MOV, DP3, DP4, CND, CMP; nop nothing; bem (1.4) BEM with the destination register's number as its stage. Sources keep their swizzles and modifiers (the GPU's codes are DirectX 8's); a result shift (x2 to x8, d2 to d8) is the shift, _sat saturate, the write mask the mask. ps 1.0-1.3's cnd reads r0.a as its token says.
- **Co-issue.** A pair (the second instruction's bit 30) becomes two instructions; its sources are read before either writes (the SDK issues the two together): where the second reads a register the first writes, that register is first copied to scratch and the second reads the copy.
- **Texture instructions, 1.0-1.3** (n < m; S, S2 scratch; t(k) is TEMP 2 + k):

| Instruction | Program |
|---|---|
| tex t(m) | SAMPLE t(m) ← COORD m, stage m, PROJECT |
| texcoord t(m) | MOV_SAT t(m).xyz ← COORD m; MOV t(m).w ← 1 |
| texkill t(m) | KILL COORD m |
| texbem t(m), t(n) | BEM S.xy ← COORD m, t(n), stage m, PROJECT (as the fixed function's bump stage projects); SAMPLE t(m) ← S, stage m |
| texbeml t(m), t(n) | as texbem, then LUM t(m) ← t(m), t(n), stage m |
| texreg2ar t(m), t(n) | SAMPLE t(m) ← t(n) swizzled (w, x, x, x), stage m |
| texreg2gb t(m), t(n) | SAMPLE t(m) ← t(n) swizzled (y, z, z, z), stage m |
| texreg2rgb t(m), t(n) | SAMPLE t(m) ← t(n), stage m |
| texm3x2pad t(m), t(n) | DP3 t(m).x ← COORD m, t(n) |
| texm3x2tex t(m+1), t(n) | DP3 S.y ← COORD m+1, t(n); MOV S.x ← t(m).x; SAMPLE t(m+1) ← S, stage m+1 |

| texdp3 t(m), t(n) | DP3 t(m) ← COORD m, t(n) |
| texdp3tex t(m), t(n) | DP3 S.x ← COORD m, t(n); MOV S.yz ← 0; SAMPLE t(m) ← S, stage m |

  A texture instruction's source modifier (bx2 on t(n), where its version allows it) goes on the t(n) operand. The pad instructions' registers hold their dot products (DirectX 8 leaves them undefined).
- **ps 1.4:** a phase's texture instructions read the registers as the phase began (the texld page asks r sources to be written in the earlier phase): where one reads an r register an earlier one of the same phase wrote, the register is copied to scratch first. texld r(m), t(n) is SAMPLE r(m) ← COORD n, stage m (its `.xyz`/`.xyw` as the swizzle, `_dw` as DW; no PROJECT: 1.4 ignores D3DTTFF_PROJECTED); texld r(m), r(n) (phase 2) SAMPLE r(m) ← TEMP n (`_dz` as DZ); texcrd r(m), t(n) MOV r(m) ← COORD n with its mask, swizzle and divide (not saturated; the range clamps it); texkill KILL of its t or r register; texdepth r5 DEPTH TEMP 5; the phase marker nothing (DirectX 8 calls the temporaries' alpha lost there and asks it written again; the GPU keeps it).

**Vertex shaders.** Registers: r0-r11 are TEMP 0-11, TEMP 12-15 the translator's scratch; v0-v15 INPUT 0-15; c(n) CONST n, c[a0.x + n] CONST n with RELATIVE; a0 ADDR 0; oPos, oD0, oD1, oFog, oPts, oT0-oT7 OUTPUT 0, 1, 2, 3, 4, 5-12.
- **Instructions:** add, sub (the assembler writes sub as add with the second source negated, but a token stream may carry sub), mul, mad, mov, dp3, dp4, min, max, slt, sge, frc, lit, dst, expp, logp, exp, log, rcp, rsq become the GPU's of the same name; mov to a0 is MOVA; nop is nothing. The scalar ones (rcp, rsq, exp, log, expp, logp) take their source's replicated component (the w selector of its swizzle, which the DDK requires to be a replicate; for a swizzle that is not one, the SDK's text and its code disagree, x or w, and the reference device decides) into x.
- **Macros** become dot products into consecutive registers of the second source's file: m4x4 four DP4, m4x3 three DP4 (x, y, z), m3x4 four DP3, m3x3 three DP3, m3x2 two DP3, each row into one component of the destination as its mask allows; a relative second source keeps RELATIVE, its register stepping. A destination that is the first source, or one of the rows, is written through scratch, so no row reads a component an earlier row wrote.
- **The declaration** of a shader with a function becomes INPUT elements: each register load (STREAMDATA) an element of index its register, of its stream at the offset the stream's tokens before it reach, of DirectX 8's type plus one (the GPU's numbering); SKIP moves the offset; CONSTMEM's constants load at every SETVERTEXSHADER (above); EXT tokens are stepped over; a tessellator stream or token, or a register loaded twice, refuses the shader (no N-patches are offered); an element reaching past MaxStreamStride makes it unusable, as a fixed-function declaration (its draws skipped and counted). One that loads no register gets one element, stream 0's first dword as FLOAT1 into an input register the function does not read (the GPU's DECLARE has an element at least). A stream's stride is SETSTREAMSOURCE's.

**Draws with a vertex program** read the streams its declaration names as any declaration's, and the user clip planes CLIPPLANE sends are the ones the program set (clip space, as DirectX 8 has them while a vertex shader is bound). The fixed-function states keep being sent as the program sets them. Shaders a program creates for software vertex processing (D3DUSAGE_SOFTWAREPROCESSING, or a device without hardware vertex processing) never reach the driver: the runtime runs them and hands it transformed vertices.

### DrawPrimitives2's DirectX 8 commands

A DirectX 8 context's call has no call vertices: `lpDDVertex` and `dwVertexType` are not used. With USERMEMVERTICES, `lpVertices` is the user memory SETSTREAMSOURCEUM names (without `dwVertexOffset`, as the DDK's sample reads it), `dwVertexLength` vertices of it. For every one of commands 45-67 the header's count is the number of records.

- **Draws.** PrimitiveCount becomes vertices or indices by the type (points n, lines 2n, a line strip n + 1, triangles 3n, strips and fans n + 2); D3DCAPS8's MaxPrimitiveCount keeps every draw within one DRAW (1M). One whose indices, from an index buffer outside the pool, are more than the index area takes, or (not indexed) whose vertices from streams outside the pool are more than the vertex area takes, goes in pieces, each its own DRAW: lists in whole primitives, strips overlapping by one or two vertices (a triangle strip's pieces from an even vertex, so their triangles keep their winding); fans are skipped. The "2" forms' byte offsets become whole vertices of stream 0's stride, the rest (a multiple of 4) a shift of stream 0's start. A draw skips, and counts why, when the vertex shader has no declaration the GPU reads, a stream it reads has no buffer, a stride is not a multiple of 4 up to 1024, an indexed draw has no index buffer, or it is larger than a DRAW or the inline buffer takes (a CLIPPEDTRIANGLEFAN above 65535 triangles, whose edge flags go in its DRAW, too).
- **Where the vertices are.** Each stream the declaration reads is the buffer its binding names: one of the DLL's in the pool (an application's vertex or index buffer) the GPU reads where it is (STREAM at its GPU address, its whole size, its version, the batch's fence on it at the call's end, or on every buffer in the pool when a batch read more than its list holds); anything else (user memory, a buffer in system memory, the runtime's own buffers, which it may write without a Lock) goes through the inline buffer: the vertices the draw reaches (its range, or from its smallest index to its largest, read for this), each stream's within its buffer, above the call's earlier ones, a window the call sent already reused when it holds them; when the windows a draw lacks do not fit above the others, all of its windows go again from the area's start (so one never overwrites another of the same draw). The buffers a call's draws bind are resolved once per call while none is recorded, forgotten or written by BUFFERBLT. When a draw has such a stream, every stream is named from the draw's first vertex, so the GPU's vertex numbers start there. An index buffer in the pool is INDICES at its GPU address; another, and a DirectX 6 or 7 command's own indices, go into the index area. So does the DirectX 8 runtime's own index buffer, through which its user-pointer draws (DrawIndexedPrimitiveUP) come as DRAWINDEXEDPRIMITIVE2: the runtime rewrites it without Locks, so its version changes only at its rare Locks. A DRAWINDEXEDPRIMITIVE2's indices always go through the ring, read at the draw; the index buffer it names, up to 64 KB (the runtime's is 4 KB), is taken for the runtime's from then on, all its draws' indices read so, no fence kept on it (the GPU never reads it); the pieces rule for index buffers outside the pool covers it too. The `buffers:` line counts the draws whose DRAWINDEXEDPRIMITIVE2 indices went through the ring, the index buffers taken (and the largest: above the runtime's 4 KB, an application's buffer a DRAWINDEXEDPRIMITIVE2 named) and the calls that drew from a buffer still locked (BUFFERBLTs and the runtime's index buffer not counted). `dbg` writes one line at a time, under the shared block's line lock, which the Glide DLLs' lines take too ([The 32-bit DLL](#the-32-bit-dll)). Buffers in system memory move into the pool, when they can, before the call takes the ring lock.
- **DirectX 6 and 7 drawing commands** in a DirectX 8 context draw from the same bindings: their vertex numbers are stream 0's, their indices (as INDEXEDTRIANGLELIST's records, with edge flags) go through the index area, and the inline vertices of the _IMM commands, in the vertex shader's FVF format, go through the inline buffer as stream 0 for that draw.
- **The GPU's records.** DECLARE, every stream's STREAM and INDICES go only when the GPU holds another (one record, for every process, kept until a reset).
- **BUFFERBLT** copies a range of one buffer into another in order with the draws: into a pool buffer that a queued packet may still read (the open batch's draws included), through fresh memory, the old contents copied and the old block freed once the GPU passed the batch; fresh memory is only a free block (under the ring lock the pool never grows); without one, the batch ends, the DLL waits for it, writes in place and starts another (the call's windows in the inline buffer dropped: another context's call may have used it meanwhile). With no batch open (the GPU held, or the context stopped) it writes in place, so the buffer is never left stale. A destination in system memory is written as it is (the ring reads it at each draw), and windows the call sent are dropped.
- **VOLUMEBLT** copies the box of the source volume to (DestX, DestY, DestZ) in the destination, for every level the two share, the box and point halved at each (the box is in the source's top level, the point in the destination's; when the destination's top is smaller in width, height or depth, the source's levels start at the one of its size, as TEXBLT's), a slice at a time as TEXBLT copies a rectangle (a BLT from video memory, an UPLOAD from system memory). A volume level's slice pitch is the one CreateSurfaceEx gave it (below) or, in system memory, DirectDraw's, never less than its rows.
- **State blocks** record SETVERTEXSHADER, SETPIXELSHADER, both constant commands, SETSTREAMSOURCE and SETINDICES with the state commands, and CAPTURE writes their current values, as the DDK's sample does (DirectX 8's driver records state blocks itself). STATESETCREATE (5) is for pure devices, which the caps do not offer.

### Volume textures and DirectX 8's formats

- **Volumes** (DDSCAPS2_VOLUME, the depth in ddsCapsEx.dwCaps4's low word; each level's depth the top's halved): CreateSurface lays every level out itself (PLEASEALLOC_BLOCKSIZE), in its own format or, with none (DirectDraw gives a surface a pixel format only when it differs from the display's), the display's: rows a dword apart, slices the rows' height apart, all of them in one block; once DirectDraw has allocated them, CreateSurfaceEx writes each video memory level's slice pitch into `dwBlockSizeY` (lSlicePitch), which the runtime locks them with. A stage's volume is TEXTURE type 2: every level's offset, pitch and slice pitch, all within video memory, else no texture (a volume CreateSurface did not lay out is none either). No sub-volume lock is offered (D3DDEVCAPS_SUBVOLUMELOCK): the runtime locks a whole volume.
- **Presentation blits.** DirectX 8's runtime flags every blit of a windowed Present DDBLT_PRESENTATION and its last DDBLT_LAST_PRESENTATION, and lets a driver queue at most three frames. The DLL keeps the fences of the last three per source surface (eight sources): a presentation blit while the oldest is pending waits for it with DDBLT_WAIT, else answers DDERR_WASSTILLDRAWING.
- **Formats** the DirectX 8 runtime describes at creation by their legacy masks or, for DirectX 8.0's signed ones, by their D3DFORMAT code as a FourCC (the DDK's "Surface Formats as FOURCC Codes"): A8 (DDPF_ALPHA, 8 bits), X4R4G4B4, A4L4 (luminance 0Fh, alpha F0h) and Q8W8V8U8 (FourCC 63); only with the DirectX 8 interface. With PROFILE.PROGRAMS also command set 2.2's V16U16 (FourCC 64, or BUMPDUDV with 0000FFFFh, FFFF0000h), G16R16 (RGB with 0000FFFFh, FFFF0000h, 0, no alpha bits, or FourCC 34) and A2W10V10U10 (BUMPDUDV with 000003FFh, 000FFC00h, or FourCC 67): the DDK names no masks for DirectX 8.1's formats, so the DLL takes either form. A FourCC one is laid out by CreateSurface, its pitch the width's bytes, a dword apart. A1R5G5B5 is a render target with it.

The **vertex race notes** come with the texture audit too. Before each DRAW that reads a pool buffer's stream by GPU address, the DLL hashes the window the draw reads, as it sends it, into a VSUM note: a NOP just before the DRAW ([gpu-commands.md](gpu-commands.md), NOP). A DirectX 6 or 7 draw from the pool's stream gets one; a DirectX 8 draw gets one for each pool stream it reads, and one for its index buffer when that is in the pool (stream FFh: the draw's indices, the index size its stride). The window is the draw's vertices; for an indexed draw, a DirectX 8 draw's declared window (MinIndex and NumVertices, when it gives them, is not sent in pieces, none of its pool streams is dynamic, and it is no more than the draw's index count plus 64: a game appending with NOOVERWRITE may declare the whole buffer), else the range its indices reach, plus its base; from the stream's address, cut at the buffer's end and to its first 64 KB. It is asked before any index is read; a window past it goes without a note. Once a draw's notes are sent, its buffers' records start again (a buffer in two streams of a draw has both notes first), so the buffer's next note names the Locks given after this draw. The sequence comes from the shared block's `note_seq` (above), for the VSUM and PROC notes alike. Each note's stream word carries the buffer's audit id, given at its creation with the texture audit (24 bits, never 0) and kept by renames. With the texture audit the DLL also sends a PROC note at each DrawPrimitives2 batch's start and before a draw, when the process is not the one the last PROC note named, and again after each new context and after the GPU lost its state (the shared block's `state_epoch` moved: a reset or a recovery): the executable's file name as ContextCreate found it for the context, 16 characters at most ([gpu-commands.md](gpu-commands.md), NOP), so the GPU's findings name the process. The report adds, while any, `texture races:` n `VSUM notes (`n `KB hashed,` n `of index buffers),` n `draws or windows without one (the budget;` n `of them quiet buffers')`. What the GPU finds: [registers.md](registers.md), Vertex race detector.

The **flight recorder** runs at every Diagnostics level but "Minimal" and "Glide": for each process (8 at once: a new process takes a free slot, else one already shown, else in turn one whose process has no live context, so one that may yet die keeps its ring; a process leaving without live contexts frees its own), its last 32 callbacks (a callback polled again by the same thread after "still drawing" one entry, with the polls counted), each with its name, thread, time (by rdtsc; the dump gives the newest's age), answer (`ok`, an error, `-` for not handled, `inside` while it runs) and two figures (Lock: the surface record and the pointer given; CreateSurface: the first surface's caps and the count; CanCreateSurface: the caps and the format's FourCC or bits; CreateExecuteBuffer: the bytes and caps2; DrawPrimitives2: the context and the commands' length, or where an unparsed call stopped; GetDriverInfo: the GUID's first dword and the bytes, a DirectX 8 request's type; ContextCreate: the context and process; Blt: the destination and flags; Flip: the two surfaces; DestroySurface, CreateSurfaceEx and the execute buffers' callbacks: their surface record); for each context, its last 32 DrawPrimitives2 commands (opcode, count, first data dword, and whether still running, faulted or unparsed). The DLL's data is one for every process, so the lines can come from another process than the one recorded. They are written (`flight:`, oldest first, a process's callbacks once and each context's commands once) when a context is destroyed after its process ended (DDHELP's clean-up after a crash), when a process is found ended with contexts (ContextCreate's reaping), at ContextDestroyAll with contexts live, when a process leaves with contexts live (DLL_PROCESS_DETACH) or without them but after an error answer among its last callbacks, when a process is found ended without a context (at each ContextCreate and each report: a crash brings no DLL_PROCESS_DETACH), and after a fault the guard caught (a process's first two, the callbacks again; the context's commands are written again at its end); with the stream audit, also when a DirectX 8 context is destroyed in its own process before it drew (a test that gave up before its first draw). A FreeLibrary's DLL_PROCESS_DETACH writes the contexts it leaves live but keeps the process's slot. A slot shown as ended that its process ID comes back to starts again (Windows 98 gives an ended process's ID again). A process's DLL_PROCESS_ATTACH and DETACH each write a line (the DETACH's kind and the callbacks recorded); a DETACH without live contexts, whatever its `reserved` (Windows 98 may pass NULL at ExitProcess), writes the process's last callbacks on one line (a tidy exit after a failure still shows what came before) and marks the slot left (DirectDraw's own clean-up may still record there), and a left slot is freed at the next reap without lines; a process found ended without a context and without leaving is written only when a callback of it never returned, an error answer came, or a process's ending DETACH has been seen; an ATTACH whose ID an unshown, died-looking slot still holds writes that slot first. The runtime's version (DXVERSION) is kept per process, as a DirectX 9 program and a DirectX 8 one can run at once.

**Shader capture**: with the card's "DirectX 8 shaders: Capture" values and Diagnostics at any level but "Minimal" and "Glide" (DEBUG's bit 3), the DLL logs each shader's instructions under the `shader:` line every such level gives it ([Diagnostics](#diagnostics); vertex shaders' too, their registers r, v, c, c[a0.x+n], a, oPos, oFog, oPts, oDn, oTn), and with "Capture, with GPU programs" (bit 4 too) the GPU program each became, a line an instruction (`shader` hash `program:` the operation with `_sat`, `_x2` to `_d8`, `_proj` and `_nc`; the destination by file and register, r TEMP, v INPUT, c CONST, a ADDR, t COORD, o OUTPUT, s STAGE, f FIXED, with its mask; the sources with their modifiers, swizzles and `[a0]`; 256 lines at most). CREATEPIXELSHADER keeps each (its tokens in the DLL's heap without their comments, up to 1024 dwords; capture alone keeps 512 shaders a context; one past those, or one the heap has no room for, is refused, counted and named, 16 a session); DELETEPIXELSHADER frees it (a bound one is unbound: the runtime may give the handle again); SETPIXELSHADER binds it; SETPIXELSHADERCONST keeps c0-c7. Both are state commands, recorded in state blocks, applied at EXECUTE and taken at CAPTURE, as the DDK's STATESET has a block hold the pixel shader and its constants. Each distinct shader (by a hash of its tokens) is logged once a session, 128 at most: its `shader:` line, then one line per instruction, 128 at most (the opcode, 1.4's texld and texcrd named so, with its result shift and saturation, the destination with its write mask, the sources with their modifiers and swizzles, a co-issued instruction marked `+`, DEF's four values, a reserved encoding as `_?`; comments left out). At its first draw (256 shaders a session) a few lines name what it draws with: the blend, alpha test and fog states; each stage it samples, reads or bumps, with its texture handle, type (2D, cube, volume), size, format and levels as the stage's handle names them now (the flush builds the stages up to the last the program samples), its coordinate index and transform flags, its addressing, filters and anisotropy (and, for a stage texbem, texbeml or bem bumps, the bump matrix, scale and offset); the specular, texture factor and wrap states; the constants it reads, DEF's over SETPIXELSHADERCONST's. A shader going names its draws. The GPU's programs draw the shaders. The `dx8 programs` lines count them ([Diagnostics](#diagnostics)). The token format is the DirectX 8 SDK's (`d3d8types.h`): the version token, instruction tokens (the opcode in the low word, bit 30 co-issue), each followed by its parameter tokens (bit 31 set; DEF's values are raw floats), comments (FFFEh with their length) and END (FFFFh).

**At Diagnostics "Minimal"**, and at "Glide" ([registers.md](registers.md), Diagnostics), DEBUG reads EVENTS (bit 5) without LISTENING at DriverInit (at Glide with bit 7, GLIDE, which only the Glide DLLs read: [glide.md](glide.md)), and the DLL counts nothing: no report, flight recorder, trace, audit, shader capture or capture asked for. It writes its event lines alone: why acceleration or Direct3D is unavailable (a shared block from another build among them); each context made (`context` n `for process` x `(`its executable's file name, `?` if Windows does not say`)`, its interface) and each process's runtime version (`a DirectX runtime of version` v); a wait over 2 seconds (again every 10 while it lasts) and a wait for a fence not yet issued or that made no progress, the callback it is in named `a callback` (the flight recorder, which knows it, is off); a reset for a GPU error (the packet refused, its context) or for no progress; the GPU found on another ring, the ring in main memory refused; a context that stops drawing; a fault caught; a lock taken over, a process that ended holding the ring lock or without destroying its contexts; the pool's failures (no pool, a grow, a release); a table full (`no room for` …), the heap (`the DLL's heap has no` n `bytes left`), a packet too long for the ring. Each place's line (its format, whatever its figures) is written its first three times, then again after 10 seconds without one from there (a table of 32 places, the last standing for every place past it), on top of each line's own limits; a line its own limits already keep to a few (a fault, its first three at each place; a GPU error, its first three of a kind; a pool grow, its first three of a step; the records' refusal, its first three; a long wait's repeats, one every 10 seconds of that wait, so a wait that lasts says so) is written by those alone, and a line's continuation (the GPU's state after a long wait or a reset for no progress, a fault's callers) goes with it. At the full levels the lines are as above. When the last Direct3D context goes the DLL writes DEBUG_IDLE, as at the full levels, so the watchdog's 5-minute "nothing sent" check stays quiet after a program ends.

## Faults inside the DLL

A fault in a callback (an access violation, a bad instruction) would otherwise reach DirectDraw's own handler, which fails the call but leaves held whatever lock the callback had taken: the next callback of any process then waits 2 seconds for the surface handle lock, or 5 for the ring lock, before taking it over. So every callback but DllMain runs inside the DLL's own fault guard:

- **The guard** is a Win32 exception frame the DLL builds itself (a record on the stack linked into the thread's chain at FS:[0]; the DLL is freestanding). Its handler declines unwinding, breakpoints and single steps (a debugger's), exceptions that are no error by their severity or are raised as noncontinuable (a C++ throw, for its own handler), and a second fault before the first was handled. For a fault it records the exception's code and address, for an access violation the address touched and whether a write, and the DLL's return addresses found on the stack (values that follow one of its call instructions: its constants share the code's section); then it resumes the guard's caller with the call abandoned, as a compiler's `__except` does: KERNEL32's RtlUnwind gives every frame above the guard's its unwinding call (a fault inside the runtime or KERNEL32 lets their own handlers clean up), the FPU's registers are emptied and its exceptions cleared (its control word kept), and the stack and registers are the guard's again. The step a callback is at is kept in its innermost guard's own record, so it is that thread's and that guard's alone.
- **The line:** `fault in` the callback (for DrawPrimitives2 `cmd` the command, `#` its number in the call and `@` its offset in the buffer, and the step it was at: the state flush, a stage's texture handle, a stream's buffer handle, the index buffer's handle, the stream audit, the packets, a buffer settled before the ring lock, a blit's handles, the render target), then the code, `at` the faulting instruction as an offset in the DLL (`+offset`; the linker's map names the function: [vglink.md](vglink.md)), `read` or `write` and the address an access violation touched; a second line, `the fault's callers`, the return addresses (up to six, innermost first). The first three at each place (the faulting instruction, the callback, the command and the step: a buffer settled and the draws that use it fault at one instruction, and each is named), and again after 10 seconds without one there; all counted (`faults caught` in the report). At every Diagnostics level but "Minimal" and "Glide" the DLL then asks 86Box for a capture ([registers.md](registers.md), DEBUG).
- **A DrawPrimitives2 command** runs inside a guard of its own, as does each bound buffer settled before the ring lock (a fault there costs the settling, and the draws that use the buffer are then named one by one). After a fault in a command this thread's locks are released, the command's packets dropped (the ring goes back to where the command began, or, if a doorbell rang meanwhile, to the last doorbell; the GPU may then hold part of what went before, so the state epoch moves and every context sends its whole state again), the call's windows and chunks in the inline buffer, its resolved buffers and the command's own flags forgotten (a fault while a BUFFERBLT had let the ring lock go leaves the rest of the call drawing nothing), and the call carries on with the next command when the faulting one's size is known (every command but those the runtime parses itself); else the call ends there with D3DERR_COMMAND_UNPARSED.
- **Any other callback,** and DrawPrimitives2 outside its commands: the batch this thread holds the ring lock for ends (what it wrote past the last doorbell dropped, a fence after the rest), the lock goes and the DLL waits for that fence (the call may not have given the buffers and surfaces it had the GPU read their own), this thread's other locks are released, and the call answers DDHAL_DRIVER_HANDLED with DDERR_GENERIC (DriverInit: the driver does not start). Locks are released by thread, not by process: another thread of the program may hold one rightly.
- **The self-test:** with the stream audit, the first ContextCreate of each process first makes a deliberate fault inside a guard, and the line says whether the guard caught it.

## Video memory addresses

A DirectDraw surface's `fpVidMem` is a flat address in the framebuffer mapping; its video memory offset for the GPU is `fpVidMem − fpPrimary`. A texture's mip levels are the chain of surfaces attached to it, each with its own address and pitch. Its colour key is the surface's source colour key, and its palette the DirectDraw palette attached to it (DirectX 6) or the one SETPALETTE gave it (DirectX 7 and 8).

## Stopping the GPU

The GPU is stopped before anything else uses the screen or video memory, with the hold bits ([gpu-registers.md](gpu-registers.md)):

- **Enable, ReEnable, Disable** (`vgpu98.drv`): take the ring lock; let the GPU finish (waiting while it makes progress); write HOLD_DRIVER with RESET; release the lock. The mode changes. At the end, clear HOLD_DRIVER. The DLL reprograms the ring on its next use.
- **A VGA mode takes the screen** (`vgpu98.vxd`, at PRE_HIRES_TO_VGA, for a full-screen DOS session and for the blue-screen message mode alike): let the GPU finish; write HOLD_VDD with RESET. When the system VM's state comes back (RESTORE_REGISTERS for the system VM), clear HOLD_VDD. This does not rely on INT 2Fh 4001h, which message mode does not send.

Meanwhile DirectDraw calls fail with DDERR_SURFACELOST, and DirectDraw restores its surfaces afterwards, as on any card.

## GDI and the GPU

Before the DIB engine draws on the screen, the display driver's access callback (the PDEVICE's deBeginAccess) reads the last fence issued and waits for it (watching ERROR, RUNNING and HELD and progress, as every wait does). Every batch ends with a FENCE, so GDI never draws under a GPU packet still writing the frame, and a process that keeps submitting cannot keep GDI waiting ([gpu-coherency.md](gpu-coherency.md)).
